# Modbus RTU「超时(毫秒)」档位扩充（新增长超时档位，5–1000ms）

> 日期：2026-09-16　状态：完成
> 关联：ADR-022 连接设置字段 / RTU profile；[2026-09-06-RTU超时默认值与Select控件.md](2026-09-06-RTU超时默认值与Select控件.md)（本变更修订其「5–100」取值描述）。纯连接设置参数扩展，无新增 ADR。

## 需求摘要

Modbus RTU 通信选项「超时(毫秒)」的固定档位在既有 `5..100`（步进 5）基础上增补 13 个长超时档位（`150/200/250/300/350/400/450/500/600/700/800/900/1000`），便于长线 / 慢设备场景选用更长请求超时。TCP 超时（`InputNumber`，50–60000ms）不受影响。

## 边界条件

- **档位集合**：`RTU_TIMEOUT_OPTIONS` = `5..100`（步进 5，20 项）+ 13 项长超时阶梯 = **33 项**，升序、无重复；默认值仍为 **50 ms**（`defaultConfig.rtu.requestTimeoutMs`，本次不改）。
- **100 → 150 之间有意留空隙**（不提供 105–145）：按待办给定档位落地；`Select` 仍仅可选列表内档位（`showSearch` 只用于过滤，不支持任意数值输入，延续 2026-09-06 决策）。
- **schema 取值 = 数值区间**（非枚举）：`settingsSchema.rtuTimeout` 与 `rtuPersistedSettingsSchema.requestTimeoutMs` 均为 `min(5).max(1000)`，上限与档位列表上限对齐（放宽容忍手改工作区/导入值）。
- 不改动：`defaultConfig` 默认值、`config/connections.json`（值 50 在范围内）、TCP 超时字段与控件、`ConnectionSettingsModal`（直接消费 `RTU_TIMEOUT_OPTIONS`）、`packages/communication` 超时实现（自 `transport.write()` resolve 后计时，与档位无关）、`packages/workspace` / `platform-api`（对 `requestTimeoutMs` 无上限校验，无迁移）、能力矩阵 / HostMessage v1 / i18n（无新文案）。

## 异常场景

- 旧工作区/配置中 RTU `requestTimeoutMs ∈ (100, 1000]`：此前经连接设置写回会被持久化 schema 拒绝（profile 保持原值），放宽后**可正常写回**（行为变宽松，属预期改善）。
- 手改工作区得到**不在档位列表**的值（如 `123`）：`profileToValues` 会直接填入该值，下拉框回显原值但选项中无此项（现状既有行为，本次不改）；`>1000`（如 `1500`）仍越界，写回被拒。
- 空值 / 非整数 / 越界：仍由表单与持久化 schema 拦截（`int().min(5).max(1000)`）。

## 性能与安全

- 纯常量与 schema 上限改动，零协议 / 跨端 / 持久化格式改动，无安全影响。下拉项由 20 增至 33，antd 虚拟列表正常承载。

## 风险与回滚

- 风险 1：antd 下拉为虚拟列表，裸点选可能命中不到未渲染项 → 缓解：先键入收窄（过滤后仅 1–2 项）再点选，并以 `^<值> ms$` 锚定断言防误选 `1000 ms`。
- 风险 2：schema 放宽到 1000 后，旧工作区 >100 的值可被写回（更宽松，已确认接受）。
- 风险 3：档位在 100 与 150 之间存在空隙（105–145 不可选）——按需求原文的有意设计。
- 回滚：改动面 = 1 个常量 + 2 处 `max` + 3 个测试助手 + 文档，`git revert` 即回原状（无 schema 迁移、无跨端契约变更）。
