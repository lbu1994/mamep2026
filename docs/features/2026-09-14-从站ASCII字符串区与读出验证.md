# 从站 ASCII 字符串区与读出验证

> 日期：2026-09-14　状态：完成
> 关联决策：ADR-030（多寄存器连续读写与范围行，字符串语义：ASCII、每寄存器 2 字符、高字节在前）

## 需求摘要

用户反馈「中文界面下读取字符串功能读出乱码」（未能提供具体寄存器/值）。为把「字符串到底能不能正常读」变成可复现、可回归的事实，在从站脚本中内置一段**连续寄存器承载的 ASCII 字符串区**，并补上「读出该字符串」的自动化用例（从站自测 + 应用真实端口 e2e），同时把字符串类型语义写进帮助与文档，避免后续再把「类型不匹配」误判为缺陷。

## 边界条件

- 字符串区：保持寄存器 `0x0010–0x001F`（16 个连续寄存器 = 32 字符），内容 `MAMEP2026 MODBUS ASCII STRING OK`（恰好 32 字符，无尾随空格，便于断言）。
- 该区间**不命中任何规则** → 按既有「规则外回退正常行为」读写均正常，**未新增规则**。
- 编码语义与实现一致：ASCII、每寄存器 2 字符、**高字节在前**、不足补空格；非 ASCII（中文等）不支持。
- 泛化：任意寄存器数量（string 类型允许 count ≥ 1），FC03 一次读 16 个寄存器（quantity ≤ 125 约束内）。
- 空值/极值：读前 4 个寄存器 = 前 8 字符（部分读用例覆盖）。

## 异常场景

- 把**数值寄存器**按 `String` 读会显示控制字符/高位字符（如 `1234` = `0x04D2` → 控制字符 + `Ò`），看起来像乱码——这是数据类型不匹配，不是缺陷；已在从站 README 常见问题与帮助正文写明。
- 非 ASCII 数据（中文）无法用 `String` 表达：输入侧直接拒绝（`DATA_STRING_NON_ASCII`），读到设备里的非 ASCII 字节也只能照字节解码。
- 从站无响应/超时等路径不受本改动影响（字符串区回退 normal）。

## 性能与安全

- 性能：无影响（仅初始值 + 测试用例；一次 FC03 读 16 寄存器 = 32 字节，远低于 125 寄存器上限）。
- 安全：com0com 仍只读使用；不改协议层 / 工作区 schema / HostMessage v1 / 能力矩阵；应用产品代码除帮助文案外零改动。

## 计划（Plan 摘要）

1. 共享核心加字符串区常量 + 编解码 + 期望帧 hex 辅助。
2. 两份从站配置追加 0x0010–0x001F 初值（与常量一致，README 标注须同步）。
3. RTU/TCP 自测各加 2 个用例（连续 16 寄存器 / 前 4 寄存器），期望帧由辅助函数推导。
4. web + electron 真实端口 e2e 各加 1 个 UI 级用例（范围行 + Type=String）。
5. 帮助 + docs/AGENTS.md §17 + 从站 README 写明字符串语义与「乱码」成因。
6. ESP32 固件同步初值（只写代码，不 build/不烧录/不跑其测试脚本）。

## 测试策略

- 新增：从站自测 2 用例 ×2（RTU/TCP）；真实端口 e2e 1 用例 ×2（web/electron）。
- 回归重点：从站自测既有项（正常区/异常区/基础表/自定义功能码/分片/延迟/无响应）、真实端口 e2e 既有全量、`packages/ui` 单测、全仓 lint / typecheck。

## 风险与回滚

- 风险：
  1. 字符串区初值与 `ASCII_STRING_REGION` 常量需手工同步（JSON 无法引用常量）→ 已在 README 与常量注释标注；e2e 期望文本取自配置本身，配置漂移不会造成假绿。
  2. 真实端口 e2e 依赖 com0com + 环境（缺环境 runner 会 SKIP 不失败）。
  3. ESP32 侧 `sdkconfig` 与 Kconfig default 须同值（本次未构建；下次 `idf.py build` 时如不一致会被重生成）。
- 回滚：改动集中在测试基建 + 帮助文案 + 固件配置字符串，`git revert` 即恢复；应用功能代码（除帮助文案）零改动，无 schema / 协议 / 能力矩阵变更。
