# 构建产物代码分割（chunk 体积优化）

> 日期：2026-09-11　状态：完成
> 关联决策：构建/性能落地，无产品语义变更；沿用 ADR-013（monorepo）与 ADR-016/050（四端渲染器独立产物目录）既有结构，未新增 ADR。

## 需求摘要

四端渲染器构建产物原为**单个 JS chunk 1,736.47 kB（gzip 529.38 kB）**，Vite 在每次构建时提示
`Some chunks are larger than 500 kB after minification`（非阻断，属前端性能/技术债）。
本次通过「重组件按需懒加载 + 依赖 rolldown 默认分包」消除该告警，并降低首屏关键路径体积：
入口 chunk 1,736.47 kB → **393.64 kB（gzip 529.38 kB → 115.81 kB）**，最大 chunk 482.95 kB（25 个 chunk）。

## 边界条件

- **四端全体**：浏览器 `dist/`、Electron `dist-electron/`、VSCode `dist-vscode/`、Android `dist-android/`
  共用 `apps/web/vite.config.ts`，改一处即四端生效。
- **不改** `chunkSizeWarningLimit`：用真实拆分消除告警，而非调阈值掩盖。
- **不改** 能力矩阵 / HostMessage v1 / 协议层 / 工作区 schema / i18n 键 / 任何 UI 行为语义。
- 首屏即渲染/启动即打开的组件**不做**懒加载：`RegisterTable`、`BottomPanel`、`AppShortcutLayer`、两条 Banner，
  以及 **`ConnectionSettingsModal`**（非 mock 启动、工作区加载完成即自动打开，属首屏路径；懒加载只会多一次
  异步跳变——实测会让「启动弹窗」晚于 e2e 等待窗口出现而引发竞态）。
- 平台 Host 与随包插件实现（`App.tsx` 静态导入的 `ElectronAppHost`/`VscodeAppHost`/`AndroidAppHost`
  - `example-panel`/`address-adjust`/`yaskawa`/`custom-function-code`）继续留首屏，改按平台动态 import
    另立 ToDoList 待办（会改变装配时序，风险独立评估）。

## 异常场景

- **非 HTTP 协议的异步 chunk 加载**：Electron 生产 `file://`、VSCode `vscode-webview://`、Android
  `https://localhost`。产物中动态 import 使用**相对说明符**（`import(\`./HelpDrawer-<hash>.js\`)`
  - `import.meta.url` 解析），四端均可解析到同目录；VSCode 侧 `getProdHtml` 的 `./assets/*.js` 正则
    同时重写 `modulepreload` 链接，`<base>` 兜底运行时相对 URL。
- **懒加载组件挂载时机**：弹窗/抽屉首次打开才挂载（chunk 按需下载），此后常驻以保留 antd 关闭动画；
  若 chunk 尚未就绪则渲染 `null`（`<Suspense fallback={null}>`，无 loading 闪烁）。
- **弹窗互相卸载**：每个懒组件各自一层 `<Suspense>`；共用同一 boundary 时任一挂起会连带卸载兄弟节点。
- **jsdom 单测**：首次动态 import 需按需转换整条依赖链（实测 HelpDrawer 链路约 4–5 s），
  默认 1 s 等待不够 → 断言显式放宽（`LAZY_MOUNT_TIMEOUT`）。

## 性能与安全

- 性能（浏览器与 Electron 实测一致）：**25 个 chunk**，入口 `index-*.js` **393.64 kB（gzip 115.81 kB）**，
  最大 chunk `jsx-runtime-*.js` **482.95 kB（gzip 159.06 kB）**——全部 < 500 kB，四端构建均无告警；
  首屏 `modulepreload` 17 条。懒加载独立 chunk：`TraceWindow` 40.96 kB、`HelpDrawer` 16.04 kB、
  `PluginManagerModal` 7.80 kB、`SettingsModal` 7.19 kB、`WorkspaceImportModal` 1.30 kB。
- 安全/权限：CSP 未改动（`script-src 'self'` / VSCode `script-src <cspSource> 'self'`），
  异步 chunk 为同源脚本；无新增网络/文件访问面。
- 安全/权限：CSP 未改动（`script-src 'self'` / VSCode `script-src <cspSource> 'self'`），
  异步 chunk 为同源脚本；无新增网络/文件访问面。

## 计划（Plan 摘要）

1. `useOpenedOnce` + 单测（渲染期派生 state，避免 `react-hooks/set-state-in-effect` 报错）。
2. 抽出 `SettingsModal`（原内联 Modal），使 Settings 也可懒加载。

4. `vite.config.ts` 分包：**最终为「不自定义 groups，用 rolldown 默认分包」**（自定义分组的失败尝试见「关键教训」）。
5. 单测/类型/构建回归 + 文档与 ToDoList 记录。

## 关键教训（分包必须做产物级验证）

**浏览器 dev 不打包，e2e-web（dev server）跑不出打包类问题——只有四端生产构建能暴露。**
本次即因此差一点带上一个致命回归：

1. **自定义 `groups` + `maxSize: 400 * 1024`（react / antd / vendor 三组）→ Electron 生产构建整体白屏**：
   体积切分把**同一个 npm 包内部的循环依赖**切到了不同 chunk，破坏类初始化顺序；
   实测报错 `TypeError: Class extends value undefined is not a constructor or null`，
   出错点在 `@ant-design/colors`（`Color` 基类与子类被分到两个 chunk）。
   e2e-web（dev）当时全绿，掩盖了该问题；`pnpm test:e2e:electron` 一跑即现形（React 根本不挂载）。
2. **「一个 npm 包一个 chunk」（`name` 函数）**：可运行，但 `antd` 单包即 **816 kB**，告警仍在；
   而 `antd` 再按目录/体积细分又会退回上面的循环依赖问题。
3. **`output.advancedChunks` 在 rolldown 1.x 已弃用**（构建打印弃用告警），非弃用形态是 `output.codeSplitting`。
4. **不要把「启动即自动打开」的弹窗也懒加载**：`ConnectionSettingsModal` 在非 mock 启动后必自动打开（首屏路径），
   懒加载只会让弹窗晚于 e2e 的固定等待窗口出现（`tests/e2e-electron/tests/workspace-persistence.spec.ts` 的
   `closeConnectionModal` 在弹窗出现前就会 no-op），导致后续点击被 `.ant-modal-wrap` 拦截而超时；
   改回静态导入后即刻转绿。

最终结论：**不自定义分包，交给 rolldown 默认算法**——它按「动态入口可达性」切分，天然不会拆散包内循环依赖，
同时把懒加载入口的独占代码留在各自 chunk（实测 31 chunk / 最大 482.95 kB / 无告警 / 四端运行正常）。

验证手段（今后调分包必做）：`pnpm build:electron` 后用 Playwright 启动 Electron 生产构建断言 `#root` 已挂载 +
无 console 错误（本次用临时脚本做过），跑 `pnpm test:e2e:electron` / `pnpm test:e2e:vscode`（生产产物）。

## 风险与回滚

- 风险：非 HTTP 协议下动态 chunk 加载（`file://` / `vscode-webview://` / `https://localhost`）——已由
  Electron 生产 e2e + VSCode 生产 webview e2e 覆盖；浏览器生产产物经 `vite preview` + 系统 Edge 实测挂载正常。
- 回滚：改动集中在 `vite.config.ts` 分包段 + `MamepApp.tsx` 懒加载段 + 3 个新增文件，
  单次 revert 即恢复；无数据/契约变更，无需迁移。
