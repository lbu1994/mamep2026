# Binary 每 8 位分组显示 + 单元格提交/粘贴后规范化

> 日期：2026-09-11　状态：完成（实施；测试执行时机由用户决定）
> 关联决策：docs/adr/ADR-051-二进制分组显示与提交后规范化.md（关联 ADR-014 地址规范化、ADR-030 范围行、ADR-031 子行、ADR-015 剪贴板）

## 需求摘要

寄存器表 Binary 类型显示时每 8 位加一个空格分组（16 位 → `00000000 11111111`，2 组；32/64 位范围行 4/8 组），
解析对称容忍空格；并按用户决策把范围扩大为「**所有类型提交/粘贴后规范化**」，使单元格文本在输入、粘贴、
读取三条路径上始终是同一种规范形式。

## 边界条件

- 宽度：1/2/3/4 寄存器 → 2/4/6/8 组；位数上限按去空白后的位数判定，超长仍 `DATA_BINARY_TOO_LONG`。
- 空值：Binary/HEX/十进制空输入 → `DATA_EMPTY`（失败保留输入）；地址空输入 → `""`（不发送请求）。
- 极大/极小：位串最长 64 位；64 位分组后 71 字符，沿用既有 `nowrap` + 省略号（用户决策不改列宽）。
- 粘贴：系统剪贴板与应用内剪贴板共用同一路径；解析失败保留原文。

## 异常场景

- 校验失败：保留用户输入 + 红框 + Tooltip（§23），不做任何规范化回写。
- 粘贴解析失败：保留原文、不新增 issue 类型；写入/编辑时按既有校验提示。
- 规范化不做舍入/截断：超范围、超小数位、非法字符仍返回结构化错误。
- 读取覆盖：读取成功后仍按当前 Type 格式化覆盖（含用户正在输入时），与规范化同源。

## 性能与安全

- 纯字符串处理（`padStart` / `replace(/\s+/g,"")` / `BigInt` 组合），无性能影响。
- 不触协议层、调度器、HostMessage v1、工作区 schema、能力矩阵；无新增权限面。

## 计划（Plan 摘要）

1. 二进制分组显示与容错解析（data-conversion）。
2. `canonicalCellText` 单一实现点：提交（单/范围行）与粘贴共用。
3. 地址提交规范化（含 DEC 去前导零）。
4. UI 调用点与 dirty 语义修正。
5. 单测更新/新增 + e2e-web 新增 2 个 spec 用例组。

## 测试策略

- 新增/修改测试：
  - `data-conversion`：分组格式化 2/4/6/8 组、容错解析（空格/制表/换行/无空格）、往返用例改分组形式。
  - `register-table`：`canonicalCellText` 表驱动（含插件类型）、地址 DEC 去零/范围/空输入、粘贴规范化。
  - `ui`：store 提交规范化、dirty 语义（`00ab` → `00AB` 不置脏）、子行二进制显示。
  - e2e-web：`binary-grouping.spec.ts`（新）、`row-editing.spec.ts`（提交规范化 + 粘贴规范化）。
- 回归重点：读取/写入路径（规范化文本必须能原值解析回来）、轮询无变化判断、剪贴板往返、范围行子行同步。
- 执行时机：**由用户决定**（docs/AGENTS.md §27）；不得谎报。

## 风险与回滚

- 风险：提交/粘贴后文本被改写属行为变更（小写 HEX 变大写、DEC 地址去前导零、二进制加空格），
  既有 e2e 中输入类断言可能需同步。
- 回滚：改动集中在 `data-conversion`（2 个格式化/解析函数）、`register-table`（3 个文件）、
  `ui`（1 个文件调用点）；无 schema / 契约 / 持久化变更，还原文件即可。
