# 15. 非功能性需求

## 15.1 性能

### 启动性能

建议目标：

- 常规设备上首次可交互时间不超过 3 秒；
- 恢复普通工作区时不应出现长时间白屏；
- 插件加载不应阻塞核心界面显示；
- 单个插件异常不应拖延整个应用启动。

### 表格性能

建议目标：

- 1000 行寄存器配置可正常滚动和编辑；
- 普通单元格编辑响应时间不超过 100 ms；
- 日志持续增长时界面仍保持可操作；
- 大量行时采用适当渲染优化；
- 切换标签页不应重复创建无必要的通信任务。

### 通信性能

1. 软件额外处理延迟应远低于实际串口或网络通信时间；
2. 请求调度不得阻塞界面线程；
3. 轮询周期小于实际完成时间时，不应无限累积任务；
4. 应展示实际刷新能力受波特率、超时、重试和行数限制；
5. 不承诺毫秒级实时控制性能。

## 15.2 稳定性

1. 单次通信错误不得造成应用崩溃；
2. 设备拔出后应用保持可操作；
3. 插件崩溃不得破坏核心工作区；
4. 日志过大时应有上限或归档策略；
5. 状态保存失败必须提示；
6. 应支持安全释放串口和 TCP 连接；
7. 关闭标签页和应用时不得遗留不可控任务；
8. 核心协议转换逻辑应具备充分自动化测试。

## 15.3 安全性

虽然产品不承担工业安全职责，仍需满足基础软件安全要求：

1. 界面代码不得直接获得不必要的系统权限；
2. 对所有用户输入进行校验；
3. 插件安装和启用需要明确提示；
4. 不默认执行未知插件；
5. 不记录不必要的敏感信息；
6. 日志导出前提醒可能包含设备地址和通信数据；
7. 不自动把调试数据上传到云端；
8. 不在用户不知情时建立外部网络连接；
9. 桌面客户端遵循 Electron 基础安全要求；
10. VSCode 插件遵循工作区信任和扩展权限约束。

## 15.4 隐私

默认情况下：

- 所有配置保存在本地；
- 不要求用户登录；
- 不采集设备通信内容；
- 不上传寄存器表；
- 不上传原始报文；
- 不上传插件私有数据。

如果未来添加遥测，必须：

1. 默认透明；
2. 明确说明采集内容；
3. 不包含原始设备报文和寄存器数据；
4. 提供关闭方式；
5. 遵守开源项目隐私说明。

## 15.5 可用性

1. 首次使用者应能在不阅读完整帮助文档的情况下完成连接、填写地址和读取寄存器；
2. 高频操作应在主界面直接可见；
3. 所有输入项应显示名称、单位、有效范围或示例；
4. 禁用的操作应说明禁用原因；
5. 错误提示应描述问题及可执行的解决方法，避免只显示内部错误代码；
6. 连接、读取、写入和轮询应提供明确的进行中状态；
7. 长时间操作应允许取消；
8. 用户执行失败的操作后，已输入内容不得被无提示清空；
9. 相同操作在浏览器、Electron 和 VSCode 三端应保持相近的名称、位置和行为；
10. 专业术语应保持一致，不应在不同界面混用不同名称。

## 15.6 可访问性

建议满足以下要求：

1. 所有核心功能均可通过键盘完成；
2. 提供清晰可见的键盘焦点；
3. 表格支持方向键、Tab 和 Shift+Tab 导航；
4. 图标按钮应提供文字说明或辅助标签；
5. 不仅依靠颜色表达在线、离线、成功、警告和失败状态；
6. 浅色和深色主题下均保持足够的文字对比度；
7. 用户缩放界面后，核心操作仍可使用；
8. 错误信息应与对应输入控件建立明确关联；
9. 动态更新的数据不应导致焦点意外跳转；
10. 周期轮询不应通过持续闪烁表达状态；
11. 尽可能兼容屏幕阅读器对常用控件和表格的识别；
12. 不要求 MVP 达成正式无障碍认证，但不得采用明显阻碍键盘用户的交互设计。

## 15.7 兼容性

### 操作系统

Electron 客户端和 VSCode 插件应优先支持：

- Windows 10；
- Windows 11；
- 当前仍受主流社区支持的 macOS 版本；
- 主流桌面 Linux 发行版。

Windows 是串口调试和 COM10 以上场景的重点验证平台。

### 浏览器

浏览器端应优先支持具备 Web Serial 能力的 Chromium 系浏览器。

如果当前浏览器不支持所需能力，产品应：

1. 在进入连接流程前完成能力检测；
2. 明确提示不支持的能力；
3. 提供可行的替代方案说明；
4. 不显示虚假的连接成功状态；
5. 仍允许用户查看界面或已有工作区数据，但不得执行不可用的串口操作。

### VSCode

VSCode 插件应声明最低兼容版本，并在不兼容时提供明确提示。

具体最低版本和支持周期在发布计划中确定，不在本 PRD 中固定。

## 15.8 可维护性

1. 三端共享的产品行为应保持一致；
2. 同一缺陷不应要求在三套独立业务实现中分别修复；
3. 平台不支持某项能力时，应通过能力差异明确表达，不应复制一套行为相近但规则不同的功能；
4. 核心 Modbus 功能与厂商私有功能必须保持边界；
5. 新增插件不应要求修改核心寄存器表的既有业务规则；
6. 工作区数据升级应考虑向后兼容；
7. 用户数据无法迁移时，应提供备份、导出或重置路径；
8. 产品发布前应对关键通信流程执行回归验收；
9. 已知限制应在发布说明中公开；
10. 详细模块依赖、数据迁移机制和接口稳定性策略由技术设计文档定义。

## 15.9 可测试性

产品功能应具备明确、可重复的验收方式。

重点覆盖：

1. RTU 连接成功和失败；
2. TCP 连接成功和失败；
3. COM10 及以上串口；
4. 功能码 03 单行读取；
5. 功能码 0x10 单行写入；
6. 写后回读；
7. 不连续地址全表读取；
8. 周期轮询启动和停止；
9. 超时和重试；
10. 无效地址和无效数据；
11. 设备断开；
12. 标签页和寄存器表恢复；
13. 三端一致性；
14. 插件加载失败隔离；
15. 大量表格行和日志记录。

测试数据和测试设备应覆盖正常响应、超时、异常响应、无效校验和连接中断。

具体测试框架、测试目录、模拟器实现和执行命令不属于本 PRD，应在技术设计文档和 AGENTS.md 中定义。

## 15.10 国际化

MVP 至少应确保：

1. 界面文本集中管理，避免文案散落在业务逻辑中；
2. 支持中文和英文界面扩展；
3. 通信术语翻译保持一致；
4. 数值输入和协议转换不受界面语言影响；
5. 十六进制地址始终按照协议规则处理；
6. 日志中的原始报文不进行本地化；
7. 时间显示可以使用用户所在环境的本地格式；
8. 导入和导出数据应使用稳定字段，不依赖当前界面语言。

MVP 可先交付一种主要界面语言，但产品结构不得阻碍后续增加其他语言。

# 17. 产品成功指标

Mamep2026 面向开发者工具场景，初期不以商业转化作为首要指标，优先关注可用性、稳定性和调试效率。

## 17.1 核心指标

1. 用户能够在首次打开产品后较短时间内完成第一次寄存器读取；
2. 不连续寄存器可以在一个表格中完成管理，无需创建多个监控窗口；
3. COM10 及以上串口场景能够正常使用；
4. 三端 RTU 核心验收场景全部通过；
5. Electron 和 VSCode 的 TCP 核心验收场景全部通过；
6. 核心通信错误不会导致应用崩溃；
7. 工作区异常丢失率保持在可接受范围；
8. 高频操作不依赖深层菜单；
9. 主要用户任务可以通过键盘和鼠标完成；
10. 核心功能具备自动化回归测试。

## 17.2 建议量化目标

正式发布前建议达到：

- P0 验收用例通过率：100%；
- P1 验收用例通过率：不低于 95%；
- 已知阻断级缺陷：0；
- 已知严重级数据丢失缺陷：0；
- 已知导致设备连接无法释放的严重缺陷：0；
- COM10 以上测试通过率：100%；
- 核心工作区恢复测试通过率：100%；
- 1000 行表格基础操作无阻断性性能问题；
- 单次通信失败不会导致未保存的寄存器配置丢失。

具体性能基准应结合测试环境记录，不应脱离硬件、操作系统和通信参数声明绝对结果。

# 18. 风险与应对方向

## 18.1 浏览器串口兼容性风险

风险：

- 并非所有浏览器和操作系统都支持 Web Serial；
- 权限机制可能导致三端串口选择体验不同；
- 后台页面可能被限速。

产品应对：

- 启动时检测能力；
- 明确展示支持状态；
- 提供 Electron 客户端作为完整替代；
- 不承诺浏览器后台精确轮询；
- 避免将浏览器端描述为全平台通用串口方案。

## 18.2 三端功能一致性风险

风险：

- 三端系统能力不同；
- 分别实现可能导致功能和错误处理逐步分叉。

产品应对：

- 统一核心产品规则；
- 差异只存在于平台适配能力；
- 建立跨端共同验收场景；
- 对不支持的能力明确隐藏或禁用；
- 不通过模拟成功掩盖平台限制。

## 18.3 通信任务冲突风险

风险：

- 周期轮询、单行读写、全表读取和插件请求可能同时发生；
- 串口无法安全处理无约束并发请求。

产品应对：

- 同一连接上的请求必须受控；
- 长任务支持取消；
- 断开时停止后续请求；
- 向用户展示繁忙状态；
- 具体调度策略在技术设计文档中确定。

## 18.4 插件安全和稳定性风险

风险：

- 第三方插件可能执行错误操作、访问设备数据或影响稳定性；
- 不同平台可用能力不同。

产品应对：

- 展示来源和权限；
- 支持禁用插件；
- 隔离插件加载错误；
- 声明平台兼容性；
- 核心产品不默认安装来源不明的插件；
- 插件不能绕过用户可见的能力提示。

## 18.5 设备误写风险

风险：

- 合法的 Modbus 写入仍可能对设备造成不可逆影响；
- 核心工具无法了解所有厂商寄存器语义。

产品应对：

- 明确产品用于开发调试；
- 对写入操作提供明显状态；
- 不自动执行未由用户触发的写入；
- 不在核心产品中硬编码危险厂商命令；
- 厂商专用操作由插件提供说明和必要提示；
- 不承诺替代设备厂商的安全操作规范。

## 18.6 Vibe Coding 质量风险

风险：

- AI 可能生成表面可运行但协议边界错误的代码；
- 多次快速变更可能破坏跨端一致性；
- AI 可能选用过时或不存在的 API。

产品应对：

- 核心行为由验收条件约束；
- 通信和转换逻辑在用户要求测试时采用测试先行；
- 所有变更通过类型检查；自动化测试执行时机由用户决定；
- 使用社区主流、文档充分的技术；
- 关键协议行为必须通过模拟设备或真实设备验证；
- AI 代理的具体执行规则在 AGENTS.md 中定义。

## 18.7 工作区数据兼容风险

风险：

- 后续新增字段或表类型可能导致旧数据无法读取；
- 应用异常退出可能产生不完整数据。

产品应对：

- 保存数据应包含版本信息；
- 升级时尽量兼容旧数据；
- 恢复失败时保留原始数据；
- 提供重置和导出入口；
- 具体数据格式和迁移机制在技术设计文档中定义。

# 19. 产品假设

当前规划基于以下假设：

1. 主要用户具备基础 Modbus 概念；
2. 主要使用场景是开发和测试，而非生产运行；
3. 单个活动连接可以覆盖 MVP 的主要需求；
4. 16 位保持寄存器能够覆盖第一阶段主要调试场景；
5. 每行独立报文比自动合并请求更符合目标用户的调试需求；
6. Electron 是能力最完整的客户端；
7. 浏览器端接受不支持 Modbus TCP 的限制；
8. VSCode 用户愿意在编辑器内使用 Webview 形式的寄存器表；
9. 用户需要恢复工作区，但不希望应用启动后自动连接设备；
10. 厂商私有能力适合通过插件隔离；
11. 产品初期不需要登录、云同步和团队权限管理；
12. 用户接受核心项目保持轻量，复杂工具以后续版本或插件提供。

如果上述假设在用户测试中被否定，应重新评估对应功能和版本优先级。

# 20. 待确认事项

以下内容仍需在产品评审或原型验证阶段确认。

## 20.1 从站地址与 Unit ID 范围

RTU 从站地址允许范围 0~255，默认 1；地址 0 允许配置（广播语义，按标准无应答）；MVP 不实现广播写入。

TCP Unit ID 允许范围 0~255，允许 255，**默认 0**（与 RTU 默认 1 不同）——MBAP Header 的 Unit Identifier 是 RTU Slave ID 的 TCP 版本，纯 TCP 通信中常被忽略（默认 0），经网关访问 RTU 从站时才是必要寻址字段。UI 字段名按协议动态显示：RTU 显示 "Slave Address"，TCP 显示 "Unit ID"。

仍待确认：

1. 地址 0 下除读写外哪些操作可用（RTU 0 为广播语义、不实现广播写入；TCP 0 为忽略寻址，语义不同，需分别说明）；
2. 插件是否可以提供厂商专用范围校验。

## 20.2 停止位和流控支持

需要通过三端能力验证确认：

- 浏览器端是否完整支持 1.5 位停止位；
- 三端对 XON/XOFF 的支持程度；
- 三端对 RTS/CTS 的支持程度；
- 不支持参数应隐藏还是禁用显示。

## 20.3 轮询间隔

1. 不设独立的全局轮询间隔配置；
2. WP 轮询间隔为 0（读完一个立即读下一个）；
3. 不提供每行独立间隔。

仍待确认：

1. 当实际通信耗时导致轮询刷新率下降时，如何向用户提示。

## 20.4 Data 列的读写交互

已确定采用 Ant Design 表格默认交互：

1. 读取结果和待写值共用同一个单元格输入区域，内容即当前值，无独立编辑态、草稿或提交事务；
2. 编辑不暂停该行轮询，读取成功结果强制覆盖单元格内容，包括用户正在输入时；
3. 读取失败时单元格内容保持不变，不做提示（通信日志照常记录失败）；
4. 写入时按当前 Type 解析单元格文本并校验 16 位范围，校验失败时提示且不清空单元格内容；
5. 写后回读成功时，回读结果按读取规则覆盖单元格；未启用回读时，写入完成后单元格保持用户输入值；
6. Type 切换不改写单元格文本；
7. Data 单元格编辑不纳入撤销/重做。

## 20.5 多标签页与连接关系

MVP 已假设所有标签页共享一个活动连接和从站地址。

仍需确认：

- 标签页是否需要保存期望的连接配置；
- 切换标签页是否提示配置差异；
- 后续是否允许标签页绑定不同设备；
- 插件是否可以请求独立连接。

## 20.6 插件 MVP 边界

MVP 仅预留架构、不对用户开放插件安装能力——插件体系维持「内置 / 受信任」边界（Manifest 驱动启停、错误隔离、平台能力声明），浏览器端使用最小插件注册表进行内部扩展验证；本地安装、安川示例插件、插件开发文档均在 V1.0 评估。

候选方向（供 V1.0 评估）：

1. 只提供内部扩展验证；
2. 支持本地安装插件；
3. 提供一个安川示例插件；
4. 提供插件开发文档；
5. 仅预留架构但不对用户开放。

如果插件安装和运行能力未达到安全和稳定要求，可以在 V1.0 继续保留扩展边界。

## 20.7 工作区导入导出

需要确认：

- MVP 是否需要导出配置文件；
- 是否支持 CSV；
- 是否支持完整工作区文件；
- 是否允许跨三端导入；
- 是否保存连接信息；
- 是否排除设备敏感信息；
- 文件格式是否作为公开兼容格式长期维护。

## 20.8 Memory Trace 和 Register Trace

TM 的 Memory Trace 追踪窗口属于核心产品能力（PRD §6.5.4）：数据列表形式（No./Data）、Buffer Size 固定档位（Continue 硬上限 10000）、Speed 滑块控制采样间隔（100~2000ms）、支持暂停/恢复（Play/Stop）与 Save 导出。

Register Trace（后续扩展）产品形式仍待确认：

- 实时曲线；
- 导出格式；
- 是否由核心产品或插件实现。

## 20.9 多标签页右键菜单

M@MEp2006 的多标签页右键菜单内容暂不明确。

Mamep2026 不需要等待原软件细节确认，可按照现代标签页通用交互设计：

- 重命名；
- 复制；
- 关闭；
- 关闭其他；
- 关闭右侧；
- 调整顺序。

最终菜单应通过原型测试确认。
