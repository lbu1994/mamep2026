# ADR-055：宿主侧插件执行面（Electron 主进程 / VSCode Extension Host）

- 状态：已实施
- 日期：2026-09-12
- 关联：ADR-038（插件存储）、ADR-039（插件框架）、ADR-042（Address Adjust 插件化）、
  ADR-043 E-6（宿主侧 codec 注入）、ADR-044（隔离执行 / 可执行插件）、**ADR-054（删除随包插件
  + 同进程执行授权；本 ADR 落地其 §7.1「宿主侧插件执行面未装配」遗留项）**
- 影响范围：`packages/platform-node`（新增宿主插件运行时）、`packages/application`、
  `apps/electron`（主进程）、`apps/vscode-extension`（扩展宿主）、
  `packages/platform-api` / `packages/domain` / `packages/platform-node`（能力矩阵）、
  `apps/web` / `apps/vscode-extension`（生产 CSP）、e2e（Electron / VSCode）、文档

## 1. 背景与问题

ADR-054 把插件统一为「用户手动安装 + 安装时选择执行模式（isolated / same-process）」，
并明确同进程执行用于贡献**同步纯函数**能力（协议 codec / 插件 dataType / 地址变换）。
当时留下的已知限制（ADR-054 §7.1）：

> Electron 主进程 / VSCode Extension Host 仍**静态 import** 插件包提供 codec/transform，
> `hostPlugins` 仍 `false`；宿主侧插件执行面待 Phase 4。

静态 import 的后果：

1. 插件未安装（或已卸载 / 已禁用）时，宿主侧仍会按插件代码解析 codec / 地址变换
   —— 与渲染端能力矩阵（已按注册表收敛）不一致，可能出现「UI 显示 OFF、宿主仍变换地址」；
2. 插件包升级后宿主侧行为不随插件清单变化（受编译期依赖约束）；
3. 违反 ADR-054 的「插件一律手动安装」模型：宿主侧存在绕过插件存储的隐式能力。

## 2. 决策

### 决策 1：Node 侧新增宿主插件运行时（`packages/platform-node/plugin`）

新增子路径入口 `@mamep2026/platform-node/plugin`（**不引入 serialport**，与 `./tcp` 同思路）：

- `plugin-local-runtime.ts`：`loadNodePluginEntry(entrySource)` —— 宿主同进程加载单文件 JS 插件
  entry（`data:text/javascript;base64,` + 动态 `import()`），结构化收窄导出
  （`manifest` + `activate` + 可选 `deactivate` / `handleToolbarAction`），
  失败返回 `PLUGIN_LOAD_FAILED`（不抛出，错误隔离）；
- `host-plugin-runtime.ts`：`HostPluginRuntime` —— 从 `PluginStorePort` 读取插件存储，
  加载「已启用 + `executionMode === "same-process"` + 有 entrySource」的插件并注册，
  向宿主会话暴露 `getCodecRegistry()` 与 `resolveAddressTransform()`。

`ctx.registries` 由宿主提供：codec（宿主会话 codec 注册表，适配 `CodecRegistry`）、
dataType（Node 侧 `createDataTypeResolver()`）、addressTransform（宿主新建注册表）。

### 决策 2：同步策略 = 集合签名比对 + 全量重建

宿主只在**集合（已启用 same-process 插件的 id + entrySource 合集）变化**时重建：
先 `unregister` 全部宿主插件，再以**新建的** dataType / addressTransform 注册表重新加载激活；
签名未变则直接返回（幂等）。

理由：`DataTypeRegistry` / `AddressTransformRegistry` **没有注销 API**，复用旧注册表会让已卸载 /
已禁用插件的变换在宿主侧继续生效（地址被静默 −1），与渲染端不一致 —— 这是必须避免的
「幽灵能力」。插件数量极少、同步很稀疏（启动一次 + 每次存储保存一次），重建成本可忽略。

已知限制：`CodecRegistry` 同样无注销 API，且是宿主会话在构造时持有的**稳定引用**，
故卸载后其 codec 仍留在宿主注册表中。该残留无害（渲染端已移除该协议入口，宿主不会再收到
该 codecId 的会话请求），如实记录。

### 决策 3：触发与装配（两端一致）

- 宿主启动时 `sync()` 一次；
- 渲染端每次 `plugin-store-save` **成功后**触发一次（`IpcDeps.onPluginStoreSaved` →
  `HostPluginRuntime.sync()`）；保存失败不触发；
- 宿主退出 / 扩展停用时 `dispose()`（注销全部宿主插件并清空注册表）。

装配点：
- Electron：`apps/electron/src/main/main.ts`（`ensureHostPlugins()`，store = 主进程
  `PluginFileStore`），会话 `resolveAddressTransform` 指向宿主插件运行时，
  并**删除对 `@mamep2026/address-adjust` 的静态 import**；
- VSCode：`apps/vscode-extension/src/extension.ts`（store = `GlobalStatePluginStore`），
  会话 `codecRegistry` 改用宿主插件运行时的注册表（基础表 codec 仍由核心注册），
  并**删除对 `@mamep2026/yaskawa-memobus-*` / `@mamep2026/address-adjust` 的静态 import**；
- 两端 `package.json` 同步移除上述插件包依赖。

### 决策 4：能力矩阵 `hostPlugins` 翻转（浏览器 / Android 维持 false）

`electronCapabilities` / `vscodeCapabilities` / `nodeHostCapabilities` /
`nodeTcpHostCapabilities` 的 `hostPlugins: false → true`，`browserCapabilities` 与
`androidCapabilities` 维持 `false`（不加载宿主插件，TECH_DESIGN §23.2）。
同时修正 VSCode `tableTypes` 中 ADR-054 未清理干净的插件表类型残留（改为仅核心 4 项 +
由渲染端 `deriveCapabilities` 叠加）。

**生效路径如实说明**：
- VSCode：RTU 会话在 Extension Host → 插件 codec / 地址变换**实际生效**（e2e 覆盖）；
- Electron：宿主侧运行时已装配（主进程加载并执行插件、resolver 已注入 TCP 会话），
  但 Electron 的 RTU 会话在 Renderer（ADR-017）、TCP 不应用地址变换（ADR-022 / ADR-042），
  故当前**无用户可见的消费路径**；执行面与生命周期由单测 + Electron e2e 覆盖。
  待「TCP 地址变换」或「TCP 插件 codec 路由」落地后自然生效（无需再改装配）。

### 决策 5（附带修复）：生产 CSP 放行 `blob:` 脚本

E2E 首次在**打包产物**中安装可执行插件时暴露：生产 CSP 仅放行了
`worker-src 'self' blob:`，而 `script-src 'self'` 会拦截 Worker 内 / 文档内对 blob: entry 的
动态 `import()`（实测报错：`Loading the script 'blob:...' violates ... "script-src 'self'"`）。
故 `apps/web/src/csp.ts` 与 `apps/vscode-extension/src/webview/prod-csp.ts` 的 `script-src`
同步放行 `blob:`（内联脚本仍禁止），并补 CSP 单测。

影响面：四端生产产物（浏览器 / Electron / VSCode / Android）共用该策略；
dev server 不注入 CSP，故此前 e2e（dev）无法暴露 —— 与本仓库既有教训一致
（**分包 / 产物 / CSP 类问题必须用生产产物验证**）。

  只加载已启用 same-process、同步能力真正注册、幂等、注入注册表同一引用、禁用 / 卸载后无残留、

  `apps/electron`、`apps/vscode-extension` ipc 各补 2 例（保存成功触发 / 失败不触发同步钩子）；
  CSP 单测补 `script-src blob:` 断言。
- e2e：
  - **Electron** 新增 `tests/e2e-electron/tests/plugin-host-execution.spec.ts`（4 例）：
    安装同进程可执行插件（主进程对话框桩 + 生产构建）→ `plugins.json` 落盘
    （`schemaVersion 4` / `executionMode: "same-process"` / entrySource）→ 重启保留 →

## 5. 已知限制与后续

1. 宿主 `CodecRegistry` 无注销 API → 卸载插件后宿主注册表保留其 codec（无害残留，见决策 2）；
2. Electron 宿主插件当前无用户可见消费路径（见决策 4）；「TCP 地址变换」与「TCP 插件 codec
   路由」为独立待办；
3. 跨进程能力回传未做：宿主插件加载失败时渲染端能力矩阵不感知，表现为该协议连接失败；
4. VSCode 插件 entrySource 存在 `globalState`（实测单插件约 0.5MB，
   VSCode 输出 `large extension state detected` 提示）——体积大的插件建议后续改用
   `globalStorageUri` 落盘（独立待办）；
5. 同进程执行的信任模型不变（ADR-054）：用户在安装确认框中显式授权，无签名校验；
   宿主进程为完整 Node 环境（Electron 主进程 / 扩展宿主），死循环 / 内存耗尽无法拦截。
