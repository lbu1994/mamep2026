# ADR-029：写后回读及延迟回读（Write Verify，每表独立配置 + 首个工作区迁移 v1→v2）

- 状态：已确认
- 日期：2026-08-26
- 决策来源：用户任务（PRD §8.3 P1「写后回读及延迟回读」§6.5.12；配置放在寄存器表上方
  工具栏、仅作用于当前寄存器表、默认写入后立即回读；按 docs/TECH_DESIGN.md §15.3 /
  docs/AGENTS.md §18.2 设计实现；迁移方案经用户确认：旧全局值迁移到各表，新表默认 ON）

## 背景

- **PRD §6.5.12**：写后回读支持 OFF / ON（立即回读）/ ON 100 ms / ON 200 ms / ON 500 ms，
  回读使用功能码 03；结果必须区分写入失败、写入成功+回读一致、写入成功+回读不一致、
  写入成功+回读失败，且**回读失败不得显示为写入失败**。
- **TECH_DESIGN §15.3**：WriteVerifyCoordinator 阶段 write → optional-delay → verify-read
  → compare；结果类型 `write-succeeded-no-verify` / `verify-matched` / `verify-mismatched`
  / `verify-failed` / `cancelled-before-verify`；延迟用可取消时钟；§15.4 写入期间暂缓同一行轮询。
- **既有实现**：`ReadVerifySettings { mode: "off"|"immediate"|"delayed", delayMs }` 已存在于
  `packages/domain`，但为 **workspace 全局**且无任何 UI 入口（实际从未生效）；`WriteOutcome`
  仅 `{ kind: "write-succeeded-no-verify" }`；`row-result.ts` 的 `WRITE_OUTCOME_STATUS`
  已预留 verify 扩展注释。
- **每表独立配置模式**：`registerRadix`（ADR-014）、`slaveAddress`（2026-08-19）已确立
  「每表字段 + sheetSchema Zod + 缺省补默认」模式；工具栏右侧设置分组已有同形态控件。

## 决策

1. **每表独立写后回读配置**：`RegisterSheet` 新增 `writeVerify: ReadVerifySettings`，随
   工作区持久化（IndexedDB 自动保存），与 `registerRadix`/`slaveAddress` 同模式。
   **默认 `{ mode: "immediate", delayMs: null }`（ON，写入后立即回读）**。
2. **首个工作区迁移 v1→v2**（`packages/workspace/src/migrations.ts`，此前迁移框架已脚手架
   但从未接线）：
   - 把 workspace 全局 `readVerifySettings` 迁移到各 `sheet.writeVerify`（旧全局值优先；
     无全局值时补默认立即回读）；删除全局字段；`schemaVersion` 1→2。
   - `parseWorkspace` 开头接线 `migrateData`（迁移在 Zod 校验前执行），IndexedDB 仓库
     自动受益；`migrateData` 修正为「跳过已应用的迁移、检测断链」（原实现要求每个迁移
     fromVersion 等于当前版本，对已是当前版本的数据会误报 MIGRATION_CHAIN_BROKEN）。
   - 迁移方案 B（用户确认）：旧工作区若有全局值则应用到其所有表（实际都是 off，旧工作区
     保持 off）；新表默认 ON。
3. **`WriteOutcome` 扩展为 5 种 kind 判别联合**（`packages/communication/src/session.ts`）：
   `write-succeeded-no-verify` / `write-succeeded-verify-matched {readValue}` /
   `write-succeeded-verify-mismatched {expectedValue, readValue}` /
   `write-succeeded-verify-failed {errorCode, userMessageKey}` / `cancelled-before-verify`。
   携带回读值以便 UI 按 §15.1 覆盖单元格。
4. **新增 `WriteVerifyCoordinator`**（`packages/communication/src/write-verify-coordinator.ts`，
   仿 BatchReadCoordinator 模式）：`writeWithVerify(sentAddress, rawValue, settings, meta)`
   → 写入（FC0x10）→（delayed 时）可取消延迟（Clock port + CancellationToken.onCancel 扩展，
   禁止散落 setTimeout）→ 回读（FC03，同一 sentAddress，`RequestSource:"write-verify"`）→
   比较。写入失败直接失败；回读失败返回 `verify-failed`（写入成功结论不变）；延迟/回读取消
   返回 `cancelled-before-verify`。`RequestSource` 新增 `"write-verify"`（通信日志来源清晰）。
5. **轮询暂缓（§18.3）**：`PollingCoordinator` 新增 `defer(key)/resume(key)`（与 inFlight
   同语义跳过该行 tick）；`SessionHostCore.writeRow` 在写入前 `defer(row.rowId)`、完成后
   `resume`——写入+回读期间暂缓同一行轮询，其他行不受影响，用户停止轮询不自动重启。
6. **跨边界契约（HostMessage v1）**：
   - `session-write-row` payload 增加可选 `writeVerify`（`sessionWriteRowPayloadSchema` +
     `readVerifySettingsPayloadSchema`，Zod 校验）；缺省=不回读（保持既有行为）。
   - `writeOutcomePayloadSchema` 扩展为 5 种 kind 判别联合；`toWriteOutcomePayload` 投影全部。
   - `RequestSource:"write-verify"` 同步进 `commLogEventPayloadSchema.source` 枚举。
   - Electron 主进程 / VSCode Extension Host 的 `session-write-row` 分发透传 writeVerify；
     preload / vscode-bridge 桥签名同步。
7. **UI（仅 `packages/ui`）**：
   - 工具栏右侧设置分组新增 antd v6 `Select`（class `table-toolbar__verify` + `Tooltip` +
     `aria-label`，仿 `registerRadix`/`slaveAddress` 模式）：OFF / ON / ON 100 ms / ON 200 ms
     / ON 500 ms，映射 `ReadVerifySettings`；`app-store` 新增 `setSheetWriteVerify`。
   - `WriteCell` 接收 `sheetId`，按本表配置调用 `host.writeRow(row, { writeVerify })`；
     回读一致/不一致时用 `applyReadValueToRow` 覆盖单元格（§15.1 单一当前值模型），
     并区分消息（`messages.writeVerifyMatched` / `writeVerifyMismatch`）；回读失败提示
     真实错误 key；`row-result.ts` `WRITE_OUTCOME_STATUS` 补全（matched→success、
     mismatched/failed→failure、cancelled-before-verify→保持原状态），verify-failed 失败态
     携带真实错误 key/detail（不再硬编码 `errors.writeVerifyMismatch`）。
   - i18n en-US（主）+ zh-CN 双语。
8. **Clock 注入**：`RegisterTableService` deps 新增必填 `clock`（遵守「禁止散落
   setTimeout」约定），由 `SessionHostCore` 注入；`communication` `CancellationToken` 扩展
   `onCancel(listener)` 订阅（非破坏性新增，供延迟可取消）。

## 备选方案

- **配置放 Connection Settings（全局）**：用户明确要求「配置选择放在寄存器表的上方、仅作用
  于当前寄存器表」，且每表独立模式已有先例。未选。
- **迁移方案 A（丢弃全局字段、所有表默认 ON）**：最简单但改变旧工作区行为（旧数据全 off）；
  用户确认选 **B**（旧全局值迁移到各表，新表默认 ON）。
- **verify 编排放 CommunicationSession.writeRegister 内部**：耦合通信会话与回读语义；既有
  coordinator 模式（BatchReadCoordinator/PollingCoordinator）更贴合分层。未选。
- **WriteOutcome 不携带回读值、UI 另行发读**：远程路径多一次 RPC 往返且时序复杂；携带
  readValue 单次往返即可覆盖单元格。未选。

## 选择理由

- **每表独立 + 默认 ON**：用户产品要求；与 `registerRadix`/`slaveAddress` 每表模式一致，
  不同表可不同策略（如校验表 ON、日志表 OFF）。
- **首个迁移 v1→v2 走既有迁移框架**：避免 schema 解析期特殊分支；迁移单向、可测；
  顺带修正了 `migrateData` 对当前版本数据的误报。
- **WriteVerifyCoordinator 放 communication**：写+回读是会话层时序编排，复用调度器与
  取消基础设施；register-table 仅负责校验/地址/配置路由。
- **轮询暂缓由 SessionHostCore 编排**：它同时拥有 polling 与 tableService，是唯一能
  defer/resume 的层；对远端路径（Electron/VSCode）同样生效（同一 core）。
- **Verify 结果携带 readValue**：满足 §15.1 回读覆盖单元格且保持远程路径单次往返。
