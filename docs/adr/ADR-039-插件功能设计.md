# ADR-039：插件可执行化与贡献点注册表（Phase A 架构地基）

- 状态：已确认（Phase A；B~F 阶段决策后续 ADR）
- 日期：2026-08-31
- 决策来源：用户任务（docs/插件功能设计.md；4 项范围确认：只实施 A 架构地基 / ADR 先行 /
  §10 待确认项逐项顺延 / 安川协议本次只搭机制不做实现）

## 背景

- **docs/插件功能设计.md**：把插件体系从「清单注册骨架」升级为「可执行 + 可扩展贡献点」架构，
  分 A~F 六阶段（A 架构地基 / B 协议扩展 / C 安川插件+表类型 / D 主题+Address Adjust /
  E P3 精选 / F 可执行插件正式化）。
- **ADR-038 边界**：插件安装入口已三端落地（仅清单注册、不执行任何脚本、无签名/信任列表、
  持久化 app 级独立存储、`plugin-store-load/save` kind）；「插件第三方代码隔离机制」为
  docs/AGENTS.md §35 待确认项，落地前安装入口维持仅清单注册。
- **现状缺口**（2026-08-31 代码调研）：`packages/plugin-api` 的 `contributions.ts` /
  `permissions.ts` / `compatibility.ts` 为空壳；`PluginManifest` 无 `apiVersion`、`contributes`
  仅固定 `panels` 且无消费方；`RequestPriority."plugin-background"` 与 `RequestSource."plugin"`
  已定义未接线；`CommunicationLogEvent` 无 `pluginId` 字段；能力矩阵 `PlatformCapabilities`
  无插件可执行/表类型/协议扩展字段；HostMessage v1 无插件运行时桥 kind。

## 决策（Phase A 范围）

1. **Manifest v2（可执行化基础）**：`PluginManifest` 新增 `apiVersion`（compatibility 判定依据）、
   `entry?: { web?: string; node?: string }`（可执行入口模块路径，Phase A 不加载）、
   `requiredCapabilities: string[]`（平台能力要求）；`contributions` 由固定 `panels` 改为
   `Record<ContributionPointId, unknown>`（key = 贡献点 ID，value = 该点 payload 单对象，经
   贡献点注册表按 ID 校验）；`permissions` 由 `string[]` 改为类型化 `PermissionId[]`。
2. **贡献点注册表（可扩展性底座，需求⑥）**：`ContributionPointRegistry`——核心经
   `registerContributionPoint(id, schema)` 注册贡献点（schema 定义在 plugin-api，保持不依赖
   UI）；插件 manifest 的 `contributes` 按已注册点校验（未登记 → `PLUGIN_CONTRIBUTION_UNKNOWN`，
   错误隔离不影响其他点）；`getContributions<T>(id)` 聚合已注册插件的有效贡献（过滤禁用插件）；
   新能力 = 核心注册新贡献点并扩展 `contributes` 类型，不破坏存量插件。
   **内置贡献点 v1（10 个）**：`panels` / `toolbarAction` / `tableType` / `protocolExtension` /
   `addressTransform` / `theme` / `settings` / `dataType` / `command` / `documentation`。
   Phase A 全部注册 schema；**6 个实现真实消费方**（panels→底部面板渲染、theme→主题装配链、
   toolbarAction→表格工具栏注入、settings→Settings 弹窗分区、command→命令分发注册表、
   dataType→类型注册表仅查询）；**4 个空消费方**（tableType / protocolExtension /
   addressTransform / documentation 仅注册 schema，B~E 阶段接线）。
3. **类型化权限枚举**：`PermissionId = "communication" | "device-write" | "workspace-read" |
"workspace-write" | "file-read" | "file-write" | "network" | "ui-contribution" | "theme"`；
   manifest 权限校验（未知权限拒绝，`PLUGIN_PERMISSION_DENIED`）；`PERMISSION_LABEL_KEYS` 供
   UI 权限 Tag 映射；消费能力到权限的强制在 PluginCommunicationApi 落地（见 6）。
4. **三级兼容判定**：`compatibility.ts` 按 `apiVersion` 输出 `"loadable" | "loadable-warning" |
"forbidden"` 三级（含原因）；不兼容 → `PLUGIN_VERSION_INCOMPATIBLE`，错误隔离不阻止其他
   插件加载。
5. **生命周期骨架（不执行入口代码）**：状态机 `registered → validating → active → deactivated →
unloaded` + 错误隔离（同步/异步异常捕获 → `PLUGIN_LOAD_FAILED` / `PLUGIN_HOOK_FAILED` →
   记录 pluginId → 禁用故障贡献点 → 核心保持可用）；`register` 可选内置同进程
   `runtime { activate(ctx), deactivate? }`（Phase A 最小执行面，仅内置插件可用）；
   **entry 文件加载与隔离机制（Worker / worker_threads / vm）属 Phase F，另立 ADR**，Phase A
   不加载任何第三方代码。
6. **PluginCommunicationApi（接通统一调度器）**：接口（read / write / batchRead / traceStart /
   traceStop）不暴露 Transport / socket 句柄；权限门（`communication`）；请求元数据
   `source:"plugin"` + `pluginId` + 默认 `RequestPriority:"plugin-background"`——首次真正接线
   `RequestSource."plugin"` 与 `RequestPriority."plugin-background"`（均已在枚举中预留）；
   `CommunicationLogEvent` 增 `pluginId: string | null` 字段（TECH_DESIGN §8.3 要求）。
   具体工厂 `createPluginCommunicationApi({ session, clock })` 落在 `packages/application`
   （plugin-api 不依赖 communication，保持分层）。
7. **能力矩阵扩展（如实声明）**：`PlatformCapabilities` 新增 `executablePlugins: boolean` /
   `hostPlugins: boolean` / `protocolExtensions: string[]` / `tableTypes: string[]`；5 处
   `Object.freeze` 声明点同步（browser / electron / vscode / nodeHost / nodeTcp）。**Phase A
   如实值**：三端 `executablePlugins=false`、`hostPlugins=false`、`protocolExtensions=[]`、
   `tableTypes=["holding-register"]`（F 阶段翻转 executablePlugins/hostPlugins，B~C 阶段扩展
   protocolExtensions/tableTypes）。
8. **HostMessage 插件桥 kind（契约一次定型）**：新增 request kind `plugin-runtime-load` /
   `plugin-runtime-unload` / `plugin-rpc` / `plugin-contribution-query` + event kind
   `plugin-event`（Zod 校验 + kind 白名单 + preload/vscode-bridge 桥 + 两端 ipc 穷尽分支）。
   **Phase A 语义**：`plugin-runtime-load` / `plugin-runtime-unload` / `plugin-rpc` /
   `plugin-contribution-query` 在宿主侧返回能力错误（`PLUGIN_RUNTIME_NOT_AVAILABLE`，
   category `plugin`），运行时语义 Phase F 补齐——契约与穷尽守卫先行，避免 F 阶段契约变更。
9. **插件存储 schemaVersion 1→2**：已装插件 manifest 迁移到 v2 字段（`apiVersion` 等补齐默认
   值）；store 数据校验同步；应用级存储不变（IndexedDB / plugins.json / globalState）。
10. **示例插件升级 v2**：`registerExamplePlugin` 演示 panels + theme 两个贡献点
    （permissions 改 `["ui-contribution","theme"]`），作为机制验证的活样例。

## 明确顺延（B~F 阶段，后续 ADR 逐项确认）

- 插件第三方代码隔离机制（Worker / worker_threads / vm + 能力白名单）——§35 待确认，Phase F；
- 安川 MEMOBUS 协议（`protocol-memobus` 包 + `ProtocolCodec` 注入 `CommunicationSession`）——
  Phase B；
- 新表类型（`tableType` 消费方 + workspace schema v4→v5 + 新建表选类型 UI + ROM/RAM Enter）——
  Phase C；
- 主题用户设置（ColorPicker + `preferences.themePrimary` 持久化）与表级 Address Adjust
  （`addressTransform` 消费方 + 逆转 ADR-013 + 新 kind + 轮询按表）——Phase D；
- P3 精选（线圈/离散/输入寄存器表、自定义功能码、Memory Access、设备描述、寄存器手册、
  数据解析接入）——Phase E；
- 可执行插件安装形态（单文件 JS → zip 扩展位）——Phase F。
- docs/插件功能设计.md §10 的 10 项待确认事项按上述归属逐项顺延，落地阶段再确认。

## 影响与边界

- **改动**：plugin-api（manifest v2 / contributions / permissions / compatibility / lifecycle /
  plugin-communication-api / store v1→v2 / registry 接线）、communication（log-event
  `pluginId`）、application（plugin-communication 工厂）、platform-api（新 payload + 4 request
  - 1 event kind + 桥）、domain（能力矩阵 4 字段）、三端（ipc 穷尽分支 + preload/桥白名单 +
    渲染端路由）、ui（6 个消费方 + PluginManagerModal 安全确认扩展 + 示例插件 v2 + i18n）。
- **不影响**：协议层零改动（无 codec 注入）；工作区 schema 零改动（无迁移）；会话/调度器既有
  语义零变化（仅新增 plugin 来源路径）。
- **测试**：plugin-api（v2 / contributions / permissions / compatibility / lifecycle / 工厂 /
  store 迁移）、communication（pluginId）、application（工厂 source/pluginId/priority）、
  platform-api（新 kind 校验/白名单）、两端 ipc（穷尽守卫 + 能力错误）、ui（消费方）、
  e2e-web（贡献点机制冒烟，无 console 错误）；存量 manifest v2 形状相关测试同步更新。

## 后续复审条件

- Phase A 验收：单测全绿 + typecheck/lint 通过 + 三端 mock e2e 无回归 + 冒烟验证（example-panel
  可见、theme 贡献生效、Plugin Manager v2 字段展示）。
- Phase F（隔离机制）落地前：安装入口不执行任何第三方代码，`executablePlugins`/`hostPlugins`
  维持 false（如实声明）。
