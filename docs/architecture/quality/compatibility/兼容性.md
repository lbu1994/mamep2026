# 兼容性设计

## 1. 兼容性设计

### 1.1 Node.js 运行环境

Electron 和 VSCode 可能使用不同 Node.js 版本。

共享 Node 平台包应：

- 避免依赖单一 Host 特有的全局变量；
- 声明最低 Node.js 版本；
- 通过构建目标分别输出；
- 对原生模块分别打包；
- 不假设 Electron 与 VSCode ABI 相同；
- 在启动时检查必要能力。

### 1.2 浏览器环境

Web 应用构建时：

- 不打包 Node.js polyfill；
- 不模拟 TCP；
- 不引用文件系统；
- Web Serial 不存在时仍允许打开只读工作区界面；
- 能力检测早于连接操作；
- 不支持的功能不创建无效入口；
- 页面刷新后保持离线。

### 1.3 工作区向后兼容

兼容策略：

- 新版本必须能够读取受支持范围内的旧 Schema；
- 旧版本不保证读取新 Schema；
- 导入较新 Schema 时显示明确错误；
- 迁移前保留原始数据；
- 插件未知字段尽可能保留；
- 删除字段需经过迁移；
- 字段语义变化不得只复用旧字段名。

### 1.4 插件兼容

插件兼容性由以下条件共同决定：

- apiVersion；
- 应用版本；
- 平台；
- 必需能力；
- 权限；
- 插件自身数据 Schema。

任何一个条件不满足时，不应尝试带病加载。

Android WebView 是否支持可执行插件不能只按版本号声明。装配期必须通过生产同一条隔离运行时路径验证 Blob Worker 创建和 Worker 内 entry 动态 import；失败、超时或异常时以 `executablePlugins: false` 启动。该探测只决定隔离插件执行能力，不把 `hostPlugins` 翻为支持。

### 1.5 操作系统支持

Electron 客户端和 VSCode 扩展优先支持：

- Windows 10；
- Windows 11；
- 当前仍受主流社区支持的 macOS 版本；
- 主流桌面 Linux 发行版。

平台支持测试必须区分“代码可构建”和“目标系统完成运行验证”。

### 1.6 浏览器能力不满足

浏览器端优先支持具备 Web Serial 能力的 Chromium 系浏览器。能力不满足时：

1. 进入连接流程前完成检测；
2. 明确提示缺失能力；
3. 说明可用的替代客户端；
4. 不显示虚假连接成功；
5. 仍允许打开和查看已有工作区；
6. 不提供可操作但必然失败的串口入口。

### 1.7 VSCode 版本兼容

VSCode 扩展必须声明最低兼容版本；不兼容时提供明确提示。最低版本和支持周期
在发布计划中确定，不在架构文档中固定为永久承诺。
