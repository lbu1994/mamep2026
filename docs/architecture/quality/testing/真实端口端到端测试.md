# 真实端口端到端测试

## 1. 定位

真实端口端到端测试使用操作系统串口、真实 TCP Socket 和独立 Modbus 从站进程验证用户主路径。它与 Mock/Fake 测试互补：

- Mock/Fake 测试覆盖业务组合、异常分支和快速回归；
- 真实端口测试覆盖浏览器授权、Electron/VSCode 宿主桥、原生串口/TCP 栈、进程边界和共享 UI；
- 虚拟串口不等于真实 USB 设备，真实端口测试也不能替代发布前的真机验收。

所有结论必须区分“用例通过”“按环境跳过”和“未执行”。缺少 com0com、端口或从站时允许 SKIP，但不得把 SKIP 记作通过。

## 2. 测试拓扑

| 路径 | 拓扑 | 主要验证点 |
| --- | --- | --- |
| RTU | `COM4 <-> COM5` com0com 环回，独立 RTU 从站占用 COM5 | Web Serial / Node Serial、系统选择、授权复用、RTU 组帧、CRC、超时与迟到丢弃 |
| TCP | `127.0.0.1:1502` 上的独立 TCP 从站 | Node `net`、MBAP 分帧、Transaction ID、Unit ID、异常响应 |
| 浏览器 | 系统 Edge + 开发服务器 + 共享 UI | Web Serial picker、真实 RTU、IndexedDB、浏览器无 TCP 入口 |
| Electron | 生产构建 Renderer/Preload/Main | Renderer Web Serial RTU、Main 远程 TCP、IPC 白名单和错误投影 |
| VSCode | Extension Host + 生产 Webview | Node Serial/TCP、HostMessage RPC、共享 UI 和主题 |

浏览器端不测试 Modbus TCP。RTU 的系统 picker 无法由 Playwright 代替，浏览器用例在一次串行运行中共享已授权 page 和活动连接，以减少重复授权。

## 3. 配置与编排

连接参数不得散落在测试中：

- 主站 RTU/TCP 参数读取仓库根 `config/connections.json` 的 `rtu-com4-master` 与 `tcp-local-slave`；
- RTU 从站端口读取 `scripts/modbus-slave/modbus-slave.config.json`；
- TCP 从站默认监听参数读取 `scripts/modbus-slave/modbus-tcp-slave.config.json`；
- 测试覆盖参数与场景规则位于从站配置和共享从站核心，不由 UI 临时拼装。

`config/connections.json` 是测试和验证脚本的外部输入，不是应用内“载入连接配置”功能，也不是工作区持久化格式。应用侧连接对象只能来自工作区 `connectionProfiles` 或设置界面。

统一入口为 `scripts/e2e-real.mjs`：

1. 读取主站与从站配置；
2. 检查 RTU 主站口、从站口或 TCP 目标是否就绪；
3. TCP 端口已被占用时，仅当 FC03 探测成功才复用现有从站；
4. 就绪后设置 `MAMEP_REAL=1`，按需启动从站并等待就绪；
5. 运行单个平台或全部平台；
6. 回收本进程启动的从站并透传测试退出码。

可用命令：

- `pnpm test:e2e:web:real`
- `pnpm test:e2e:electron:real`
- `pnpm test:e2e:vscode:real`
- `pnpm test:e2e:real`

真实用例还必须自行检查 `MAMEP_REAL=1`，防止被普通 E2E 套件误收集。`?mockTransport=1`、`MAMEP_FAKE_SERIAL=1` 和 `MAMEP_FAKE_TCP=1` 是显式开发/测试手段，与真实端口门控互斥且不得成为默认路径。

测试状态也必须显式建立，不能从前一用例的残留继承：

- 每次运行先清理临时工作区、应用日志和 `plugins.json` 等会影响业务入口的持久状态；
- 插件由随应用分发改为用户手动安装后，真实端口套件不得假设可选插件已经存在；
- 依赖插件贡献的用例先构造“未安装”基线，再通过真实安装入口完成安装和授权，
  最后断言贡献可见；需要同步 codec/dataType 的插件必须走同进程执行路径；
- 套件的 `pretest`/`pretest:real` 必须构建其引用的插件产物，干净环境中的单套件运行
  不能依赖前一个全量步骤碰巧生成过 `release/plugins/`；
- 昂贵连接可在同一串行运行内复用，但每个用例在复用前必须断言所需连接和工作区基线。

## 4. 共享从站

RTU 与 TCP 从站复用 `scripts/modbus-slave/lib/modbus-core.mjs` 中的寄存器规则、异常、CRC、日志和行为投递，避免两种传输出现不同测试结论。

默认规则至少覆盖：

- 正常读写区；
- 只读或只写受限区；
- 读写均返回 Modbus 异常的区域；
- 写值门控和异常码；
- 无响应以触发请求超时与重试；
- 地址 `0x0000` 与 `0xFFFF` 边界；
- 写成功但回读不一致。

真实从站还可按区间配置：

- `delayedResponse`：延迟响应，用于验证总超时窗口之后的迟到帧被丢弃；RTU 延迟必须大于“单次超时 × 尝试次数”的重试窗口；
- `splitResponse`：将响应拆成多个片段，用于验证半包/粘包组帧；
- must-multi 区：单寄存器访问返回异常，多寄存器连续访问成功，用于验证范围行。

从站核心与 RTU/TCP 入口均应提供自检，规则变更先通过自检再进入三端真实测试。

## 5. 场景矩阵

每个适用平台和协议应覆盖共享 UI 级闭环：

1. 打开 Connection Settings，按能力选择和填写真实参数；
2. 建立连接并确认状态、通信属性与日志；
3. FC03 正常读取；
4. FC0x10 写入、写后回读并确认单元格值；
5. Modbus 异常码；
6. 超时、重试以及后续请求恢复；
7. 迟到响应被丢弃；
8. 分片响应的正确重组；
9. 地址边界；
10. 范围行一次连续读写；
11. 通信日志中的真实请求/响应字节；
12. 断链、重连和资源释放；
13. 全程无未处理页面异常、`console.error`、CSP 违规或 React 警告。

浏览器 RTU 用例不做跨运行自动选择串口。可在 `localStorage` 记录上次选择用于诊断和运行内复用，但每次新运行仍需用户完成一次系统授权。

## 6. 平台差异

### 6.1 浏览器

使用有头系统 Edge，因为 Web Serial picker 不能由 headless 自动化可靠触发。测试应在 Connection Settings 的端口控件范围内触发授权，避免误点其他 Select。

### 6.2 Electron

测试生产构建路径。RTU 通过 Renderer Web Serial 与 Main 的授权协调完成；TCP 通过 Preload/Main 的 HostMessage 会话 RPC 完成。用例应断言协议路由正确，且 Renderer 未获得 Node.js 通用能力。

### 6.3 VSCode

使用真实 VS Code 实例和生产 Webview。VSCode Webview 可能包含容器 frame 与承载共享 UI 的内容 frame，定位器必须落到含 `#root`、`.ant-app` 或共享布局的内容 frame，不能只按 `vscode-webview://` 前缀选择容器。

VSCode 通常是两层嵌套 iframe，共享 UI 及 antd 挂在 `document.body` 的 Dropdown、
Popover、Select 等 portal 也位于最内层内容 frame。取得 `waitForWebviewFrame()` 返回的
frame 后，所有 UI 定位都必须使用 `frame.locator(...)`；`frame.page().locator(...)`
只查询顶层文档，不能用于 Webview 内元素。文本输入优先使用目标控件的元素级 `fill()`，
不依赖窗口级键盘焦点。`frame.page().keyboard` 只可用于确实需要窗口键盘语义的操作。

每个 VS Code fixture 启动成本较高时，可按协议合并为单测试并用 `test.step()` 覆盖多个场景，但断言仍必须达到 UI 级。测试驱动第三方 API 发生版本漂移时，应使用已记录的 pin/patch 并验证真实启动，不得把基础设施异常解释为产品失败或通过。

### 6.4 共享布局分支

平台名称不能决定使用桌面布局。共享 UI 依据实际 Webview 宽度切换 1023px 断点；
VSCode 侧栏展开后可能进入移动布局，Electron 正常窗口则仍是桌面布局。真实端口
helper 必须按实际可见布局适配，而不是把某一端的套件固定写成桌面路径：

- 移动布局中，地址进制、Unit ID、写后回读等次要控件可能位于工具栏“更多”面板；
  打开面板完成操作后应关闭，避免遮挡表格；
- 底部面板可能位于带遮罩的 Drawer；操作表格前先关闭 Drawer，完成设备动作后再打开
  并切换目标页签进行断言；
- 桌面与移动分支共用同一业务场景，布局 helper 负责展开/收起临时浮层，不能复制两套
  产品操作流程或改变协议断言；
- 新增响应式断点或在 toolbar、Drawer 中移动控件时，必须重跑 VSCode real suite，因为
  浏览器与宽窗口 Electron 可能都无法暴露该回归。

## 7. 稳定性与诊断规则

- 新引入或改动的大型 E2E 套件必须以完整可执行回归作为验收，不以“文件已创建”“环境 SKIP”或零散用例通过代替全量执行。
- real 套件与主 E2E 套件共享 UI 语义；控件组件变化时必须同步所有选择器。例如进制切换当前使用 Segmented，而不是 Select。
- 同名控件必须限定在 `Form.Item`、工具栏或其他业务容器内。串口下拉不能按页面首个 Select 定位。
- Select 选项必须做精确文本匹配。存在 `100 ms` 与 `1000 ms` 等前缀重合档位时，
  不能键入模糊值后依赖 Enter 的落点；应先在可见 dropdown 内精确过滤，再等待目标项
  visible 后点选。
- 虚拟列表只渲染视口内容。断言历史通信日志时，应先清空日志，再重建目标帧并等待可见，不能依赖已被滚出视口的 DOM。
- 编辑后立即提交时，提交处理不得依赖尚未刷新的 React render state。受控编辑器应同步维护最新草稿，保证真实快速输入和自动化 `fill` 后 Enter 都提交同一值。
- 测试等待应基于业务状态、请求完成、日志出现或进程就绪信号；固定等待只可作为外部门控或已知平台时序的有限兜底。
- 全量串行执行造成高负载时，受控弹窗可能持续重排，导致 Playwright 行动性检查在稳定
  与 detached 之间重试。应优先缩小作用域并等待明确前置状态；仅对已限定、确实会因
  宿主负载重渲染的弹窗控件，才允许跳过 actionability。跳过时仍必须保留完整鼠标事件
  序列，因为 antd Select 依赖 `mousedown` 展开；DOM `element.click()` 或 `evaluate`
  不能作为替代。
- 失败后应回收 page、连接、从站和临时工作区，避免残留会话或遮罩污染后续用例。
- Playwright 用例失败可能重启 worker 并重跑 `beforeAll`。后续用例不得把“前一用例成功
  后留下的连接或页面状态”作为隐式前置；需要共享状态时，应在该用例开头显式验证或重建。
- 报告应保存执行命令、环境可用性、各平台通过/失败/跳过数量、从站启动情况和原始失败日志。
