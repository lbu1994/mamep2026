# 依赖库管理

## 1. 依赖库管理

### 1.1 依赖选择原则

关键依赖必须满足：

1. 社区主流；
2. 文档完整；
3. TypeScript 支持良好；
4. 许可证允许开源和分发；
5. 最近仍有维护；
6. 安全问题可追踪；
7. 支持目标 Node.js 和浏览器版本；
8. 不依赖不可控的云服务；
9. 不引入特殊 DSL；
10. 能够被自动化测试替代或封装。

### 1.2 依赖封装

以下关键依赖必须经过项目适配层：

- 串口库；
- IndexedDB 库；
- Electron IPC；
- VSCode API；
- 表格库；
- 国际化库；
- 插件加载器；
- 文件保存实现。

不得让第三方库对象成为领域模型或持久化格式。

Node.js 串口库已确定为 `serialport@13`。`serialport`、`@serialport/bindings-cpp` 和 `@serialport/stream` 只能由 `packages/platform-node` 封装；Domain、Application、UI、工作区和插件公开契约不得出现其类型、实例或原生句柄。pnpm workspace 必须显式允许该原生绑定构建。

Electron 与 VSCode 的 Node ABI 不同，不能共享已编译绑定。接入或升级时必须分别在对应 Host 环境安装/重建，并验证打包产物能够加载原生模块。

Electron 打包工具链的兼容 override 应放在 `pnpm-workspace.yaml`。当前 pnpm 11 不读取根 `package.json` 的 `pnpm` 配置；若 electron-builder 与 `@electron/get` 存在版本声明冲突，使用 workspace override 暂时收敛并记录移除条件，不在业务代码中规避。

### 1.3 版本策略

- 使用明确版本范围；
- 锁定文件进入仓库；
- 关键依赖升级单独评审；
- 串口、Electron、VSCode 和表格依赖升级按用户要求执行专项回归；
- 不自动接受关键依赖的主版本升级；
- 删除不再使用的依赖；
- 定期检查许可证和已知漏洞。

具体升级命令和代理执行步骤属于 AGENTS.md。
