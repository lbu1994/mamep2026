# 代码规范

## 1. 类型和错误

TypeScript 必须保持严格类型检查，核心模块不得用弱化编译配置换取通过。

- 禁止隐式 `any`，核心模块原则上禁止显式 `any`；
- 捕获的异常先按 `unknown` 处理，并在边界处收窄；
- 外部输入进入领域层前必须经过运行时校验；
- 跨进程、跨 WebView 消息使用可辨识联合类型；
- 序列化数据使用字符串联合类型，不使用 TypeScript `enum`；
- ID、寄存器地址和原始值使用明确的领域类型或受控工厂函数；
- 不得用无意义类型断言或非空断言掩盖未处理状态；
- 对外接口明确返回值和结构化错误模型；
- 第三方库类型、实例和句柄不得成为领域模型或持久化格式。

错误对象、错误分类和用户信息边界见[领域模型](../domain/领域模型.md#3-错误模型)。

## 2. 命名

- 类型、类和 React 组件使用 `PascalCase`；
- 函数、变量和实例使用 `camelCase`；
- 常量遵循仓库现有规范，使用 `camelCase` 或 `UPPER_SNAKE_CASE`；
- 布尔值使用 `is`、`has`、`can`、`should`、`supports` 等明确前缀；
- Port 接口使用清晰的能力名称并以 `Port` 结尾；
- Adapter 使用平台和能力命名；
- 错误代码使用稳定的大写下划线形式；
- 持久化字段名称不得依赖当前界面语言；
- 避免 `data`、`info`、`temp`、`obj` 等缺乏上下文含义的名称。

插件标识、协议标识、表类型标识和工作区字段一旦形成持久兼容契约，改名必须配套迁移。

## 3. 函数和文件

- 一个函数只承担一个明确职责；
- 复杂业务分支拆成可命名、可测试的单元；
- 避免超大文件、超大组件和超大 Store；
- 不得创建没有明确边界的通用工具集合；
- 纯函数优先放入可独立测试的核心包；
- 平台副作用集中在 Adapter 或 Host；
- 注释说明设计原因、边界和风险，不重复代码表面行为；
- 删除无用注释、调试日志、临时代码和已失效 TODO。

模块职责和依赖方向见[系统设计总览](../总览.md#5-系统总体架构)与[模块依赖规则](../总览.md#8-模块依赖规则)。

## 4. 格式化和静态检查

- 使用仓库统一的 Prettier 和 ESLint 配置；
- 不为单个文件创建冲突的格式规则；
- 不通过大面积禁用规则让检查通过；
- 必要规则例外必须说明原因并限制到最小范围；
- 格式化修改不得与无关功能修改混在同一次变更中。

静态检查只证明相应规则通过，不能替代协议、通信、持久化和跨端行为验收。
