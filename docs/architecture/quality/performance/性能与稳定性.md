# 性能与稳定性

## 1. 性能目标

性能目标用于指导实现和回归，不等同于脱离硬件、操作系统、串口参数和网络
环境的绝对承诺。

### 1.1 启动性能

- 常规设备上首次可交互时间目标不超过 3 秒；
- 恢复普通工作区时不应长时间白屏；
- 插件加载不得阻塞核心界面显示；
- 单个插件异常不得拖延整个应用启动；
- 应用启动后保持离线，不因恢复工作区产生设备请求。

### 1.2 表格性能

- 1000 行寄存器配置可正常滚动和编辑；
- 普通单元格编辑响应时间目标不超过 100 ms；
- 日志持续增长时表格仍保持可操作；
- 大量行采用虚拟化和细粒度订阅；
- 标签页切换不重复创建无必要的通信任务。

### 1.3 通信性能

- 软件额外处理延迟应远低于实际串口或网络通信时间；
- 请求调度不得阻塞 UI 线程；
- 轮询周期短于实际完成时间时不得无限积累任务；
- UI 应展示实际刷新能力受波特率、超时、重试和行数影响；
- 不承诺毫秒级实时控制性能。

### 1.4 稳定性目标

- 单次通信错误不得导致应用崩溃；
- 设备拔出后应用保持可操作；
- 插件崩溃不得破坏核心工作区；
- 日志和 Trace 缓冲必须有上限或归档策略；
- 状态保存失败必须提示且保留内存状态；
- 串口和 TCP 连接必须可以安全释放；
- 关闭标签页、页面、窗口或扩展时不得遗留不可控任务；
- 核心协议与转换逻辑必须具备自动化测试。

## 2. 表格与界面性能

实现措施：

- 行虚拟化；
- 细粒度 Store Selector；
- 稳定 `rowId`；
- 避免单行读取结果导致整个表格重渲染；
- 单元格文本局部更新；
- 日志与表格状态分离；
- 低频保存使用 debounce；
- 批量粘贴作为一个事务；
- 计算型格式化函数缓存或按需执行。

性能验收至少覆盖：

- 1000 行；
- 1000 行中多行周期更新；
- 大量日志；
- 多标签页切换；
- 深色主题；
- 浏览器缩放；
- VSCode Webview。

## 3. 日志与 Trace 性能

- 消息日志、通信日志和 Trace 分别使用有界缓冲；
- 日志列表虚拟化；
- 合并批量事件更新；
- 用户手动离开底部时暂停自动滚动；
- 原始字节延迟格式化；
- 导出在 Host 或 Worker 中执行；
- 不为每个字节创建独立 React 节点；
- Trace 缓冲上限 10000 条，不允许无限增长。

## 4. 通信性能

- Electron 的远程通信在生产路径中由主进程承载；
- VSCode 远程通信由 Extension Host 承载；
- Browser 中不得以同步长任务阻塞 UI；
- CRC、MBAP 和帧解析使用 `Uint8Array`；
- 通信热路径不进行大型 JSON 序列化；
- 日志事件可批量推送到 UI；
- 轮询复用有限数量的 Clock/Timer；
- 所有设备请求统一进入 RequestScheduler。

## 5. Worker 使用边界

MVP 不强制引入 Web Worker。以下任务达到性能瓶颈后可迁移到 Worker：

- 大型日志导出；
- 大型工作区导入校验；
- Trace 数据处理；
- 大量数据格式转换；
- 曲线降采样。

串口和 TCP 通信仍由对应 Host 能力负责，不因 Worker 引入新的平台业务分叉。

## 6. 性能回归要求

性能回归应记录运行环境、数据规模、平台和通信参数，至少验证：

1. 启动和恢复工作区；
2. 1000 行滚动、编辑、粘贴和键盘导航；
3. 大量行持续更新与轮询；
4. 日志和 Trace 达到上限后的内存占用；
5. 标签页切换；
6. VSCode Webview；
7. 断开、页面隐藏和恢复后的任务数量；
8. 性能优化不改变领域模型、公共契约和平台能力语义。
