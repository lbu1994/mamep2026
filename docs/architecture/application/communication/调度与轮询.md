# 请求调度与周期轮询

## 1. 请求调度与并发控制

### 1.1 单连接单队列

每个活动连接拥有一个 RequestScheduler。

当前只有一个活动连接，因此运行时只有一个主要请求队列。

所有来源的请求必须进入同一队列：

- 单行读取；
- 单行写入；
- 全表读取；
- 周期轮询；
- 写后回读；
- 插件请求。

不得绕过队列直接调用 Transport。

### 1.2 调度目标

1. 同一时刻只执行一个设备请求；
2. 用户手动操作不被大批轮询任务长期阻塞；
3. 轮询任务不能无限积压；
4. 全表读取可以取消；
5. 断开时取消队列；
6. 写后回读保持操作关联；
7. 插件请求不能垄断通信链路；
8. 请求执行顺序可测试；
9. 超时后能够继续处理后续请求；
10. 迟到响应不会关联到错误请求。

### 1.3 请求优先级

建议定义以下优先级：

1. connection-control；
2. manual-write；
3. manual-read；
4. write-verify；
5. batch-read；
6. polling；
7. plugin-background。

优先级只能影响尚未开始的任务，不中断已经发送到设备的请求。

为避免低优先级任务饥饿，应采用带公平性的优先级队列，例如：

- 高优先级请求优先；
- 连续执行一定数量高优先级请求后允许较低优先级请求执行；
- 同优先级按创建顺序执行；
- 插件不得指定超出其权限的优先级。

具体公平参数作为内部实现配置，不进入 PRD。

### 1.4 不允许重复积压的轮询任务

每一个轮询行在队列中最多存在一个待执行任务和一个可能正在执行的任务。

如果下一次轮询触发时，上一次任务仍在等待或执行：

- 不追加新的同类任务；
- 记录一次 skipped tick 或 lag 指标；
- 保留下一轮重新调度机会；
- UI 可展示实际刷新速度低于配置速度。

这可以避免链路变慢时队列无限增长。

### 1.5 手动快速点击

对同一行连续快速点击读取时：

- 如果已有同一行的手动读取尚未开始，可以合并为一次；
- 如果已有读取正在执行，可以禁用按钮或将后续请求合并；
- 不应无上限创建相同请求。

对写入操作不自动合并，因为每次写入可能代表用户的独立意图。

UI 在写入请求未完成时默认禁用该行的再次写入按钮，除非后续明确设计写入队列功能。

### 1.6 请求取消

每个任务持有 CancellationToken。

取消分为：

- 尚未开始：直接从队列移除；
- 已在附加延迟阶段：终止等待；
- 已发送请求：停止等待结果并标记取消；
- 底层 Transport 不支持撤回已经发送的字节，因此取消不等于设备未执行；
- 取消后到达的响应必须被识别为迟到响应并丢弃或记录。

用户断开连接时：

1. 阻止新任务入队；
2. 取消所有未开始任务；
3. 取消当前等待；
4. 关闭 Transport；
5. 清理接收缓冲；
6. 发布取消和断开事件。

## 2. 超时、重试和接收延迟

### 2.1 超时

每次协议请求拥有独立超时。

超时从实际发送完整请求后开始计算，不从进入队列时开始计算。

需要分别记录：

- queueWaitMs；
- writeDurationMs；
- responseDurationMs；
- totalDurationMs。

连接超时和请求超时是不同配置，不得共用同一个错误类型。

### 2.2 重试

重试规则：

1. retryCount 表示首次请求失败后允许的额外尝试次数；
2. 每次尝试使用新的 attempt 编号；
3. TCP 请求重试使用新的 Transaction ID；
4. RTU 请求重试清理当前请求的接收缓冲状态；
5. 每次尝试单独记录日志；
6. 最终结果记录累计耗时；
7. 用户取消后不再重试；
8. 用户主动断开后不再重试；
9. 参数校验错误不重试；
10. 明确的 Modbus 异常响应默认不重试；
11. 超时、临时连接错误和可配置的传输错误可以重试；
12. CRC 错误是否重试由 RetryPolicy 明确决定。

### 2.3 请求间隔

相邻请求之间不设接收延迟或 `interRequestDelayMs`。

- 相邻请求之间无附加延迟（上一请求结束后立即开始下一请求）；
- 不用于判断帧结束；
- 不替代请求超时；
- 不影响已收到响应的解析。

## 3. 周期轮询设计

### 3.1 轮询模型

周期轮询采用：

- 每行独立启用状态（WP 开关）；
- 轮询间隔为 0，读完一个立即读下一个；
- 不设独立的全局轮询间隔配置，不提供全部行持续轮询（ALL Polling）；
- 单连接；
- 每行单独功能码 03 请求；
- 不合并连续地址。

PollingCoordinator 管理需要轮询的行，但不直接访问 UI 表格。

每个轮询目标至少包含：

- workspaceId；
- sheetId；
- rowId；
- address；
- slaveAddress 或 unitId；
- enabled；
- generation；
- nextDueAt。

### 3.2 Generation 机制

当发生以下操作时增加行的 generation：

- 修改地址；
- 修改所属标签页；
- 删除行；
- 停止轮询；
- 切换连接；
- 修改影响请求目标的配置。

轮询结果返回时，只有 generation 与当前行一致才允许更新行状态。

结果事件必须携带完整绑定身份：`sheetId`、行键、实际发送地址、发送时的
`RequestRoute`、请求 generation 和连接 generation。协调器在目标地址、Unit ID、
协议或所属表变化时使旧 generation 失效；Host 边界再次按当前表路由校验，UI 仅在
校验通过后才写入成功/失败状态与行数据。Read All 同样使用每行的真实地址，不得用
地址 0 作为绕过校验的哨兵值。

该机制防止：

- 修改地址后旧响应覆盖新地址；
- 删除行后迟到响应重新创建状态；
- 关闭标签页后旧任务更新已销毁页面；
- 断开并重连后旧请求污染新连接。

### 3.3 轮询间隔语义

技术层将轮询间隔固定为 0：每个启用行在上一轮完成后立即重新加入轮询（读完一个立即读下一个）。

由于所有请求串行执行，实际刷新周期由请求往返时间决定。

调度器不保证严格实时性。

每行记录：

- configuredIntervalMs（恒为 0）；
- lastScheduledAt；
- lastStartedAt；
- lastCompletedAt；
- actualIntervalMs；
- skippedTicks；
- lastSuccessAt。

### 3.4 标签页切换

切换标签页不自动停止其他标签页的轮询，因为轮询状态属于工作区行为而非可见性行为。

关闭标签页时：

1. 停止该标签页所有轮询；
2. 取消尚未执行任务；
3. 已发送任务的返回结果不得更新已删除标签页；
4. 保存新的工作区状态。

轮询范围策略可通过替换协调策略调整，不改变底层队列。

### 3.5 全部轮询控制（不提供）

不提供全部行持续轮询（ALL Polling）功能。

轮询仅由每行 WP 开关控制。一次性全表读取（Read All）由 BatchReadCoordinator 实现，是一次性批量操作，不进入轮询调度。

停止轮询：

- 通过关闭各行的 WP 开关停止该行轮询调度；
- 关闭标签页时取消该标签页尚未执行的轮询任务；
- 不取消用户手动读取和写入；
- 不断开连接。
