# 全表读取与写后回读

## 1. 全表读取设计

BatchReadCoordinator 负责全表读取。

处理流程：

1. 获取当前标签页不可变行快照；
2. 对每行执行地址校验；
3. 创建有效行任务；
4. 统计空行和无效行；
5. 按表格顺序提交读取；
6. 每行独立执行；
7. 单行失败后继续；
8. 发布进度；
9. 支持取消尚未执行的任务；
   （本地路径由共享 `BatchReadCoordinator` 取消；远程路径见下）
10. 输出批次摘要。

> 范围行（多寄存器）：`BatchReadRow` 携带 quantity，范围行在
> 单次请求内读完全部连续寄存器（不跨行合并）；结果以 `values[]` 回传并按组合类型格式化；
> 单行失败不中断批次的原则不变。

批次摘要至少包含：

- batchId；
- totalRows；
- eligibleRows；
- successCount；
- failureCount；
- skippedCount；
- cancelledCount；
- startedAt；
- completedAt；
- durationMs。

### 1.1 本地与远程取消

本地浏览器/Electron RTU 路径直接持有 `BatchReadHandle`。取消令牌作用于整批所有行：

- 尚未开始的任务从调度队列移除；
- 已发送的请求停止等待结果并记录取消；
- 已到达但属于已取消请求的响应按迟到响应隔离。

远程 Electron TCP 与 VSCode 路径使用同一句柄接口，但通过 HostMessage 协作：

1. Renderer 创建 handle 时生成 `batchId`；
2. `session-batch-read` payload 携带 `{ batchId, rows }`；
3. 宿主 `SessionHostCore` 把活动 handle 登记到 `batchId -> handle` 映射；
4. 行结果继续经既有 `poll-result` 事件上报，请求响应返回批次摘要；
5. UI 取消按钮调用 `handle.cancel()`，触发 `session-batch-cancel { batchId }`；
6. 宿主查到活动 handle 后调用同一取消实现；
7. promise 完成或失败后注销映射，避免泄漏。

取消是“软件停止等待”，不保证已经发送的设备请求没有执行。未知、已完成、已断开或重复的
`batchId` 都必须是安全 no-op。取消后仍应以批次摘要中的 `cancelledCount` 告知最终结果。
UI 在任务运行期间保留 Read All loading，并提供独立取消入口；取消后重新发起读取时，
旧 promise 不得覆盖新任务状态。

全表读取和轮询同时存在时：

- 全表读取优先级高于普通轮询；
- 不清空轮询配置；
- 轮询任务不得重复积压；
- 批量完成后轮询继续；
- 对同一行的临近重复读取允许由调度器去重。

## 2. 写入与写后回读设计

### 2.1 Data 单元格单一当前值

Data 单元格采用单一当前值模型，不再区分读取值与待写草稿：

- 单元格内容即当前值，用户编辑直接改值；
- 读取成功后按当前 Type 格式化，强制覆盖单元格内容，包括用户正在输入时；
- 读取失败时不改变单元格内容，不做提示；
- 同一时刻只存在一份单元格文本，禁止在领域模型中为读取值和待写值维护两份独立文本。

用户开始编辑时：

1. 不创建独立草稿；
2. 该行不进入独立编辑状态；
3. 轮询结果直接覆盖单元格内容；
4. UI 无需区分实时值与待写值。

### 2.2 写入流程

1. 创建行快照；
2. 校验连接；
3. 校验地址；
4. 根据 Type 解析 Data 单元格当前文本；
5. 转换为 16 位原始值（范围行解析为多个原始值）；
6. 创建具有当前活动表写后回读配置的写入请求（范围行为多值写，一次写全部连续寄存器）；
7. 进入统一队列；
8. 记录请求和响应；
9. 根据 Read Verify 规则决定是否回读；
10. 更新写入状态；
11. 写入失败不清空单元格内容。

### 2.3 写后回读

写后回读是 `RegisterSheet.writeVerify` 的每表设置，随工作区持久化并通过工具栏控制，
只作用于当前表。支持的语义为：

- OFF：不自动回读；
- ON：写入后立即回读；
- ON 100 ms / 200 ms / 500 ms：写入后等待指定时间再回读。

新表默认立即回读。旧工作区的全局 `readVerifySettings` 迁移到各表；没有旧全局值的表使用
新默认值。配置缺失时必须通过 Schema 默认值或迁移得到明确策略，不能在运行中猜测。

`WriteVerifyCoordinator` 将写入和回读视为相关但独立的阶段：

- write；
- optional-delay；
- verify-read；
- compare。

结果类型必须区分：

- write-failed；
- write-succeeded-no-verify；
- write-succeeded-verify-matched；
- write-succeeded-verify-mismatched；
- write-succeeded-verify-failed；
- cancelled-before-verify。

回读失败不能修改写入阶段的成功结论。

等待 100、200 或 500 ms 时使用可取消时钟，不直接使用散落的 setTimeout。

范围行一次 FC0x10 写全部子寄存器（`values[]`），回读 FC03 读 N 个连续寄存器并逐项比较。
`WriteOutcome` 的 verify 结果携带 `readValues`/`expectedValues` 数组；单寄存器使用长度 1
数组的同一结果模型。匹配时 UI 用回读值覆盖单元格；不一致或回读失败时保留写入成功的前置
事实，并分别展示对应提示。

### 2.4 写入和轮询冲突

编辑不停止该行轮询，读取结果直接覆盖单元格内容。

写入任务提交后：

- 同一行的普通轮询任务暂缓；
- 写入及其回读完成后恢复；
- 其他行轮询可以继续；
- 如果用户停止轮询，则写入完成后不得自动重新启用；
- 如果行地址在写入过程中被修改，返回结果只能关联原请求快照，不能覆盖新地址状态。
