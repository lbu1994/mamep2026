## 2. 持久化设计


### 2.1 自动保存

AutoSaveCoordinator 监听可持久状态变更。

策略：

1. 对连续编辑采用 debounce；
2. 关键结构操作可立即触发保存；
3. 应用关闭前尝试 flush；
4. 每次保存生成完整一致的工作区快照；
5. 不在保存过程中读取正在变化的可变对象；
6. 保存失败发布结构化错误；
7. 保存失败不得清除内存状态；
8. 自动保存不对外展示保存状态，仅手动保存场景展示保存中、已保存和失败状态；
9. 保存操作串行执行；
10. 新保存请求到来时合并中间状态，只保存最新快照。

关闭窗口或页面进入后台时，共享组合根监听 `visibilitychange`，仅在
`document.hidden === true` 时调用 `AppHost.flush()`。浏览器、Electron 和 VSCode
渲染上下文共用这条路径；`pending` 清空后 flush 幂等。

不使用 `pagehide` 作为可靠落盘时机。异步 IndexedDB 写入可能在卸载时被中断，
而 reload 也会触发 `pagehide`，可能把已被测试或用户清空的数据重新写回。崩溃
没有可靠 graceful 时机，不伪造“崩溃前已保存”；最多 500 ms 的未保存编辑由
自动保存兜底。系统不通过 dirty/异常退出标记区分崩溃与正常关闭。


### 2.2 数据版本和迁移

每个工作区包含 schemaVersion。

加载流程：

1. 解析 JSON；
2. 检查基础结构；
3. 读取 schemaVersion；
4. 顺序执行迁移；
5. 使用当前 Schema 校验；
6. 创建迁移后备份；
7. 返回领域对象。

迁移必须：

- 单向；
- 可重复测试；
- 跳过已经应用且版本不低于当前输入版本的迁移；
- 检测迁移链缺口，不能把“数据已是当前版本”误报为断链；
- 不直接修改原始文件；
- 保留未知插件配置；
- 记录迁移历史；
- 遇到无法迁移数据时尽可能部分恢复。

迁移链把工作区全局 `readVerifySettings` 复制到每张表的 `writeVerify`，再删除全局
字段；有旧值的旧表保持原策略，没有旧值的表使用关闭回读默认值。迁移同时将单值
`lastKnownRawValue` 转换为 `registerValues`，并补齐 `registerCount=1`。

当前工作区 Schema 继续按结构变化提升版本；已经实现的主要版本差异包括各表写后回读、范围行、表类型、地址变换、插件数据类型、主题预设、位级名称/注释。具体当前版本以 `workspaceSchemaVersion` 常量为准，文档不得复制一个容易过期的固定数字作为持久化契约。

当前迁移涉及的持久字段包括：

- 每表 `type`，核心表类型或插件命名空间表类型；
- 每表 `addressTransform`，用于表级地址变换配置；
- 行级 `registers` 范围子行元数据；
- 行级 `bitComments` 与 `bitNames`，结构按寄存器和 bit 索引；
- `preferences.themePrimary`，保存主题预设 ID 或 `null`。

缺失的可选字段优先通过 Schema 默认值补齐；需要改变字段语义或数据形状时提升
Schema 版本并建立单向迁移。插件表或插件数据类型未知时不得猜测其语义，也不得
把它静默替换成核心类型。

范围行的 `registers` 子行元数据属于持久字段，而不是可随时重建的 UI 缓存；单寄存器行为
`null`，范围行长度必须与 `registerCount` 一致。旧数据缺少该字段时由迁移或 Schema 默认值
补齐，并明确子行 Type 的继承来源。范围长度调整时按索引保留、截断或补齐元数据，原始值
不得与新的寄存器范围错位。

新增带默认值的可选字段可以保持现有版本并依赖 Schema 默认值。例如 `RegisterSheet.registerRadix` 缺失时默认 `"dec"`，老数据无需迁移。`selectedRowIds`、当前选中单元格、打开中的 Drawer、撤销栈和连接运行状态属于会话状态，不得写入工作区。

界面语言属于 `preferences.language`，当前值域为 `"en-US" | "zh-CN"`，默认和回退语言为 `en-US`。该设置应随工作区持久化，并通过启动缓存避免首帧语言闪烁。

### 2.3 损坏恢复

仓储加载主数据失败时，当前实现按以下边界恢复：

1. 尝试读取备份；
2. 备份有效时恢复工作区，并记录 `source: "backup"`、恢复时间和可用的备份时间；
3. 主文件和备份都不可用时返回默认新工作区，并记录 `source: "fresh"` 与
   结构化错误码；
4. 主数据有效时记录 `source: "none"`，不显示恢复横幅；
5. 恢复元数据通过仓储旁路 `getRecoveryInfo()` 获取，不改变
   `Result<Workspace>` 的 load 返回约定；
6. 恢复横幅只说明来源和时间，不提供操作按钮；
7. 重置仍走 Settings，工作区导入导出仍走独立交换格式；
8. 不因单个插件配置损坏而放弃全部工作区；无法恢复的字段使用明确默认值并
   记录告警。

当前恢复范围不包含完整恢复模式：不保留损坏原文件供导出，不提供“导出损坏文件”
或“进入恢复模式”入口，也不区分正常关闭与崩溃。备份轮转、原子保存和加载失败
不得删除现有有效数据。

## 3. 工作区持久化实现约束

必须覆盖：

- 浏览器 IndexedDB 保存和恢复；
- Electron 原子文件写入；
- VSCode workspaceState 和工作区文件；
- 数据损坏恢复；
- Schema 迁移；
- 1000 行、多标签页工作区保存性能；
- 异常退出后的恢复能力；
- 插件配置不存在时的兼容行为；
- 三端导入同一工作区数据的可行性。
