## 2. 持久化设计

### 2.1 自动保存

AutoSaveCoordinator 监听可持久状态变更。

策略：

1. 对连续编辑采用 debounce；
2. 关键结构操作可立即触发保存；
3. 应用关闭前尝试 flush；
4. 每次保存生成完整一致的工作区快照；
5. 不在保存过程中读取正在变化的可变对象；
6. 保存失败发布结构化错误；
7. 保存失败不得清除内存状态；
8. 自动保存不对外展示保存状态，仅手动保存场景展示保存中、已保存和失败状态；
9. 保存操作串行执行；
10. 新保存请求到来时合并中间状态，只保存最新快照。

关闭窗口或页面进入后台时，共享组合根监听 `visibilitychange`，仅在
`document.hidden === true` 时调用 `AppHost.flush()`。浏览器、Electron 和 VSCode
渲染上下文共用这条路径；`pending` 清空后 flush 幂等。

工作区恢复、导入和保存共用一个可复用解析 Worker。启动时 Worker 与 Host/UI 模块
并行预热，避免读取到 IndexedDB 快照后才加载迁移链与 Schema 校验器。保存时
`serializeWorkspaceSnapshot` 在一次执行中生成文件字符串与 IndexedDB 对象，
只执行一次完整 Schema 校验；主线程不得为提速改用未校验序列化。

不使用 `pagehide` 作为可靠落盘时机。异步 IndexedDB 写入可能在卸载时被中断，
而 reload 也会触发 `pagehide`，可能把已被测试或用户清空的数据重新写回。崩溃
没有可靠 graceful 时机，不伪造“崩溃前已保存”；最多 500 ms 的未保存编辑由
自动保存兜底。系统不通过 dirty/异常退出标记区分崩溃与正常关闭。

### 2.2 数据版本和迁移

每个工作区包含 schemaVersion。

加载流程：

1. 解析 JSON；
2. 检查基础结构；
3. 读取 schemaVersion；
4. 顺序执行迁移；
5. 使用当前 Schema 校验；
6. 创建迁移后备份；
7. 返回领域对象。

迁移必须：

- 单向；
- 可重复测试；
- 跳过已经应用且版本不低于当前输入版本的迁移；
- 检测迁移链缺口，不能把“数据已是当前版本”误报为断链；
- 不直接修改原始文件；
- 保留未知插件配置；
- 记录迁移历史；
- 遇到无法迁移数据时尽可能部分恢复。

迁移链把工作区全局 `readVerifySettings` 复制到每张表的 `writeVerify`，再删除全局
字段；有旧值的旧表保持原策略，没有旧值的表使用关闭回读默认值。迁移同时将单值
`lastKnownRawValue` 转换为 `registerValues`，并补齐 `registerCount=1`。

当前工作区 Schema 继续按结构变化提升版本；已经实现的主要版本差异包括各表写后回读、范围行、表类型、地址变换、插件数据类型、主题预设、位级名称/注释。具体当前版本以 `workspaceSchemaVersion` 常量为准，文档不得复制一个容易过期的固定数字作为持久化契约。

当前迁移涉及的持久字段包括：

- 每表 `type`，核心表类型或插件命名空间表类型；
- 每表 `addressTransform`，用于表级地址变换配置；
- 行级 `registers` 范围子行元数据；
- 行级 `bitComments` 与 `bitNames`，结构按寄存器和 bit 索引；
- `preferences.themePrimary`，保存主题预设 ID 或 `null`。

缺失的可选字段优先通过 Schema 默认值补齐；需要改变字段语义或数据形状时提升
Schema 版本并建立单向迁移。插件表或插件数据类型未知时不得猜测其语义，也不得
把它静默替换成核心类型。

范围行的 `registers` 子行元数据属于持久字段，而不是可随时重建的 UI 缓存；单寄存器行为
`null`，范围行长度必须与 `registerCount` 一致。旧数据缺少该字段时由迁移或 Schema 默认值
补齐，并明确子行 Type 的继承来源。范围长度调整时按索引保留、截断或补齐元数据，原始值
不得与新的寄存器范围错位。

新增带默认值的可选字段可以保持现有版本并依赖 Schema 默认值。例如 `RegisterSheet.registerRadix` 缺失时默认 `"dec"`，老数据无需迁移。`selectedRowIds`、当前选中单元格、打开中的 Drawer、撤销栈和连接运行状态属于会话状态，不得写入工作区。

界面语言属于 `preferences.language`，当前值域为 `"en-US" | "zh-CN"`，默认和回退语言为 `en-US`。该设置应随工作区持久化，并通过启动缓存避免首帧语言闪烁。

TM/WP 选择仅在当前应用打开期间有效。**Base behavior**：行字段 `traceEnabled` 和
`pollingEnabled` 随工作区保存并恢复。**Current behavior**：
[序列化](../../../../packages/workspace/src/schema.ts) 保留字段及现有 Schema 版本，
但固定写入 `false`，不修改当前内存中的选择；
[恢复](../../../../packages/workspace/src/hydrate-workspace.ts) 将两个字段设为 `false`，
忽略旧数据中的 `true`。所有表均遵循此规则，包括关闭的表。自动保存、导出、启动恢复、
备份恢复和导入共用这些路径；重新打开应用或刷新网页后不恢复 TM/WP 选择。

### 2.2.1 默认表名与编号

**Base behavior**：初始表及删除全部表后的补建表名为 `Sheet 1`，新增表按工作区现有表数生成
`Sheet N`；删除表后可能复用编号，连续复制同一表也可能重名。

**Current behavior**：[UI 命名服务](../../../../packages/ui/src/sheet-naming.ts) 读取核心表类型的
英文翻译，去掉末尾 `(R/W)`、`(R)` 或 `(W)`，生成 `<英文表类型> Sheet <编号>`。
例如 `HOLDING REGISTERS Sheet 1`、`COILS Sheet 1`。界面语言切换不改变名称。
插件分组新建入口传入英文标题；没有标题的直接调用使用完整表类型 ID。
名称显式传入领域表工厂；宿主创建新工作区时使用相同的初始保持寄存器表名。

工作区可选字段 `sheetNameCounters` 按完整表类型 ID 保存下一个编号，值必须为正安全整数。
[Schema](../../../../packages/workspace/src/schema.ts) 为旧数据补空对象，保持现有 Schema 版本。
[Store](../../../../packages/ui/src/app-store.ts) 加载时按同类型现有表名末尾的 `Sheet N` 求最大值，
取该值加一与已保存计数中的较大值；兼容旧 `Sheet N` 名称，不修改已有表名。
新建前检查整个工作区的已占用名称，包括关闭的表和其他类型的表，跳过冲突后推进本类型计数。
计数达到安全整数上限时拒绝分配，不回绕或复用旧编号。

删除、重命名和撤销不降低计数。删除某个核心类型的最后一张表时，补建同类型空表并使用
下一个编号；撤销恢复原表原名，重做复用已记录的补建表，不再分配编号。复制保留源表类型，以 `<源表名> Copy`
命名；冲突时依次尝试 `Copy 2`、`Copy 3`，并检查所有表。复制不消耗默认表名计数。
计数随自动保存和工作区导入导出保留；加载、恢复和命名不触发设备连接或写入。

### 2.2.2 删除最后一张同类型表

**Base behavior**：仅在工作区完全无表时补建保持寄存器表；撤销删除时移除补建表，
重做时重新生成表及名称。

**Current behavior**：[Store 删除与历史路径](../../../../packages/ui/src/app-store.ts)
对 `holding-register`、`coil`、`discrete-input` 和 `input-register` 按类型统计所有表，
包括关闭的表。删除该类型的最后一张表时，在原位置补建同类型默认空表并切换活动表。
空表使用该类型的默认行数、数据类型和表配置，不复制原表数据。

删除原表、补建空表和切换活动表合并为一个历史步骤。撤销移除该步骤记录的补建表，
恢复完整原表、原位置和删除前的活动表；完整原表包括行数据、表配置、列宽、列序和打开状态。
其他表保持不变。重做复用首次删除的补建表，包括表 ID、行 ID、名称和活动表选择。
撤销新增或复制导致某核心类型无表时，也补建同类型表；重做新增或复制时移除该补建表。

插件类型不按类型自动补建。删除插件表导致整个工作区无表时，沿用保持寄存器空表兜底。
启动完成时补齐缺少的核心类型，见下节；导入操作本身不补齐。
补建名称分配失败时，原表、活动表和历史保持不变。

### 2.2.3 启动时补齐核心表

**Base behavior**：首次启动只创建保持寄存器表；恢复工作区时不补齐其他核心类型。

**Current behavior**：[Store 的 `setLoaded`](../../../../packages/ui/src/app-store.ts)
在发布 `loaded=true` 的同一次更新中调用
[`ensureCoreSheets`](../../../../packages/ui/src/sheet-naming.ts)。
首次启动和已有工作区恢复均补齐缺少的四种核心类型，关闭的表也计入已有类型。
新表追加在原表之后，使用类型默认配置和下一个可用名称；保留原表、行数据和有效活动表。
插件表不补建。本步骤不进入撤销历史，复用加载完成时已有的自动保存，不增加保存调用。

补齐只读取已有表的类型、名称、编号和顺序，不访问已有行数据。四种类型齐全时直接返回
原工作区对象；有缺失时共用名称集合和计数，仅为缺少类型创建默认行。补齐不增加异步等待、
模块依赖、设备请求或额外 Store 更新，也不提前挂载非活动表格内容。

重置工作区也复用 `ensureCoreSheets`。
[Settings 重置入口](../../../../packages/ui/src/components/SettingsDrawer.tsx) 在宿主重置成功后，
先补齐返回工作区的核心表，再通过一次 `setWorkspace` 更新界面并清空撤销、重做历史。
新表使用重置工作区的默认名称计数，插件类型不补建。重置失败时保留当前工作区和历史。

### 2.3 损坏恢复

仓储加载主数据失败时，当前实现按以下边界恢复：

1. 尝试读取备份；
2. 备份有效时恢复工作区，并记录 `source: "backup"`、恢复时间和可用的备份时间；
3. 主文件和备份都不可用时返回默认新工作区，并记录 `source: "fresh"` 与
   结构化错误码；
4. 主数据有效时记录 `source: "none"`，不显示恢复横幅；
5. 恢复元数据通过仓储旁路 `getRecoveryInfo()` 获取，不改变
   `Result<Workspace>` 的 load 返回约定；
6. 恢复横幅只说明来源和时间，不提供操作按钮；
7. 重置仍走 Settings，工作区导入导出仍走独立交换格式；
8. 不因单个插件配置损坏而放弃全部工作区；无法恢复的字段使用明确默认值并
   记录告警。

当前恢复范围不包含完整恢复模式：不保留损坏原文件供导出，不提供“导出损坏文件”
或“进入恢复模式”入口，也不区分正常关闭与崩溃。备份轮转、原子保存和加载失败
不得删除现有有效数据。

## 3. 工作区持久化实现约束

必须覆盖：

- 浏览器 IndexedDB 保存和恢复；
- Electron 原子文件写入；
- VSCode workspaceState 和工作区文件；
- 数据损坏恢复；
- Schema 迁移；
- 1000 行、多标签页工作区保存性能；
- 异常退出后的恢复能力；
- 插件配置不存在时的兼容行为；
- 三端导入同一工作区数据的可行性。
