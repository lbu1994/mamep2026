# Modbus 协议设计

## 1. packages/protocol-modbus

包含：

- Modbus RTU ADU 编解码；
- Modbus TCP ADU 编解码；
- PDU 编解码；
- 功能码 03 请求和响应；
- 功能码 0x10 请求和响应；
- 功能码 01 / 02 / 04 / 0F 请求和响应；
- 线圈与离散输入位打包；
- CRC-16；
- Modbus TCP MBAP Header；
- 异常响应解析；
- 响应一致性校验；
- 报文长度校验；
- 事务 ID 校验；
- Unit ID 和 Slave Address 校验。


## 2. Modbus 协议设计

### 2.1 实现范围

当前协议核心实现：

1. Modbus RTU；
2. Modbus TCP；
3. 功能码 03；
4. 功能码 0x10；
5. 功能码 01，读取线圈；
6. 功能码 02，读取离散输入；
7. 功能码 04，读取输入寄存器；
8. 功能码 0F，写入多个线圈；
9. 单个或多个连续 16 位保持寄存器读取与写入；
10. Modbus 异常响应；
11. RTU CRC-16；
12. TCP MBAP Header；
13. 请求和响应一致性校验。

协议数量限制遵循 Modbus PDU：

- FC03 单次读取数量为 1 至 125；
- FC04 单次读取数量为 1 至 125；
- FC0x10 单次写入数量为 1 至 123；
- FC01 / FC02 单次读取位数为 1 至 2000；
- FC0F 单次写入线圈数为 1 至 1968；
- 范围行必须在构造请求前验证起始地址加数量不越界；
- 一次 FC03/FC0x10 请求按协议整体成功或整体返回异常，不产生“部分寄存器成功”的领域结果。

单寄存器是 `quantity=1` 的特例。通信层保留单值便利方法时，它们必须委托多值实现，
不能形成两套编解码路径。

FC01/FC02 的响应数据按 byte count 承载位值：`byteCount = ceil(quantity / 8)`，
每个数据字节从 LSB 到 MSB 依次对应连续位地址；FC0F 的请求数据使用同一打包规则。
不得把位响应直接解释为 16 位寄存器值，也不得在数量边界外侧错误保留填充位。

### 2.2 表类型与核心 codec

保持寄存器使用 FC03/FC0x10 codec。线圈、离散输入和输入寄存器是核心内置表类型，
分别经 `modbus-basic-tables:coil`、`modbus-basic-tables:discrete-input`、
`modbus-basic-tables:input-register` codec 接入同一 `CommunicationSession`：

| 表类型 | 读 | 写 | 值语义 |
| --- | --- | --- | --- |
| `holding-register` | FC03 | FC0x10 | 16 位原始值 |
| `coil` | FC01 | FC0F | 0/1 |
| `discrete-input` | FC02 | 不允许 | 0/1，只读 |
| `input-register` | FC04 | 不允许 | 16 位原始值，只读 |

**Base behavior**：基础表 codec 仅支持 RTU；TCP 会话只接受标准保持寄存器路由。

**Current behavior**：基础表协议 ID 保持不变。TCP 连接上的基础表请求由
[`BasicTablesTcpCodec`](../../../../packages/communication/src/basic-tables-tcp-codec.ts)
编码为 MBAP 帧；RTU 连接继续使用 `BasicTablesRtuCodec`。两种承载共用
[`pdu.ts`](../../../../packages/protocol-modbus/src/pdu.ts) 的功能码、位打包和响应校验，
各自封装负责 CRC 或 MBAP 校验。协议包不读取 UI 表或平台状态。

[`CommunicationSession`](../../../../packages/communication/src/session.ts) 在请求入队前
固化协议 ID 和 Unit ID，并校验基础表数量、地址范围及线圈值。只读表写入直接失败，
不会发送报文。TCP 保持寄存器与基础表共享一个调度器和事务号序列；每次重试使用新的
事务号。`TcpFrameParser` 按 MBAP Length 处理分片和连续帧，丢弃事务号、Unit ID、
功能码或响应内容不匹配的完整帧，继续等待当前请求，直到有效响应或超时。

[`TcpSessionHost`](../../../../packages/application/src/tcp-session-host.ts) 为 Electron
Main、VSCode Extension Host 和 Android 的共享入口。单行、批量、轮询、Trace 与
写后回读保留表路由，进入同一会话。此路径只接受核心基础表，不把 RTU 插件 codec
用于 TCP。浏览器仍不提供 TCP 连接。

不得在核心协议包中加入：

- BCC；
- CHECK-SUM；
- 厂商私有功能码；
- Enter RAM；
- Enter ROM；
- 厂商寄存器语义；
- 私有报文封装。

Address Adjust（ON 时发送地址 = 用户地址 − 1，默认 OFF）由 register-table 应用层实现，协议包只接收最终已验证的实际发送地址。

### 2.3 协议层次

协议处理分为：

1. 领域请求；
2. PDU；
3. ADU；
4. Transport 字节流；
5. 响应帧；
6. 领域结果。

读取请求转换流程：

    ReadHoldingRegisterCommand
    -> Function 03 PDU
    -> RTU ADU 或 TCP ADU
    -> Transport
    -> RTU ADU 或 TCP ADU
    -> Function 03 Response PDU
    -> RawRegisterValue

写入请求转换流程：

    WriteHoldingRegisterCommand
    -> Function 0x10 PDU
    -> RTU ADU 或 TCP ADU
    -> Transport
    -> RTU ADU 或 TCP ADU
    -> Function 0x10 Response PDU
    -> WriteAcknowledgement

### 2.4 请求模型

每个通信请求至少包含：

- requestId；
- connectionId；
- protocol；
- source；
- operation；
- target；
- timeoutMs；
- retryCount；
- createdAt；
- cancellationToken；
- metadata。

source 用于区分：

- manual-read；
- manual-write；
- batch-read；
- polling；
- write-verify；
- plugin。

operation 用于区分：

- read-holding-register；
- write-holding-register。
- read-coils；
- read-discrete-inputs；
- read-input-registers；
- write-multiple-coils。

target 至少包含：

- slaveAddress 或 unitId；
- registerAddress；
- registerCount。

`registerCount` 为 1 时使用普通单寄存器行；大于 1 时表示一次连续访问的范围行。
协议层不得依赖 UI 表格结构或自动跨行合并请求。

### 2.5 响应校验

RTU 响应必须校验：

1. 最小帧长度；
2. CRC；
3. Slave Address；
4. 功能码；
5. 异常功能码；
6. 字节数；
7. 数据长度；
8. 写入响应中的起始地址；
9. 写入响应中的数量；
10. 是否存在多余或缺失字节。

TCP 响应必须校验：

1. Transaction ID；
2. Protocol ID；
3. Length；
4. Unit ID；
5. 功能码；
6. 异常功能码；
7. 字节数；
8. 数据长度；
9. 写入地址；
10. 写入数量。

### 2.6 RTU 帧读取

串口字节流可能分多次到达，不能假设一次 data 事件包含完整响应。

RTU Transport Adapter 应提供字节缓冲，通信会话根据当前请求推导预期响应长度。

需要处理：

1. 响应被拆分为多个数据片段；
2. 一次收到完整响应；
3. 收到多余字节；
4. 收到上一个请求的迟到响应；
5. 收到噪声或非法前缀；
6. CRC 错误；
7. 超时前只收到部分帧；
8. 设备断开。

对于当前已接线的功能码，可以根据响应头确定完整帧长度：

- 功能码 03：根据 byte count 推导；
- 功能码 0x10：响应长度固定；
- 功能码 01 / 02：根据 byte count 推导，并校验其等于
  `ceil(quantity / 8)`；
- 功能码 04：根据 byte count 推导，并校验其等于 `quantity × 2`；
- 功能码 0F：响应长度固定，并校验起始地址和数量；
- 异常响应：长度固定。

不得仅依赖固定延迟判断帧结束。

### 2.7 TCP 帧读取

TCP 是字节流协议，必须处理：

1. 半包；
2. 粘包；
3. 多个响应连续到达；
4. 连接中断；
5. MBAP Length 非法；
6. Transaction ID 不匹配；
7. 超时后的迟到响应。

TCP Adapter 应维护接收缓冲，根据 MBAP Header 中的 Length 分帧。

会话层由 `TcpFrameParser` 解释 MBAP，负责：

1. 半包等待和粘包拆分；
2. 多响应连续到达；
3. Length 非法时拒绝并重新同步；
4. 与当前请求 Transaction ID 不匹配的迟到响应丢弃；
5. 连接关闭或重建时清空不完整缓冲。

Transport Adapter 只负责原始字节、连接状态和错误映射；MBAP 业务校验、Transaction ID 与
请求关联属于通信会话，不把 Modbus 协议语义下沉到 Node `net` 适配器。

### 2.8 Transaction ID

Modbus TCP Transaction ID 由 CommunicationSession 维护。

要求：

1. 在 16 位范围内递增并回绕；
2. 单连接内唯一关联当前未完成请求；
3. 响应必须与当前请求 Transaction ID 匹配；
4. 超时后的迟到响应不得被后续请求误接收；
5. 连接重建后重置或重新初始化；
6. Transaction ID 不进入持久化工作区。

每次实际尝试，包括超时后的重试，都必须分配新的 Transaction ID。RTU 没有事务 ID，
每次重试必须清理或隔离上一尝试的接收状态；迟到 RTU 帧不得作为下一次请求的响应。
