# Mamep2026 项目需求研究

## 项目目标

复刻优化安川Mamep2006调试工具体验，打造一款轻量化、易上手、可插件化扩展的Modbus开发调试工具，面向**开发人员自用场景**，无工业设备安全管控需求，无需严苛工业级品质标准。支持**浏览器端、Electron桌面客户端、VSCode插件端**三端部署适配，兼容Modbus TCP、Modbus RTU双协议，修复原厂软件已知功能性BUG，淘汰老旧Windows经典控件与菜单设计，适配现代桌面软件审美。针对不同客户端的运行环境限制做差异化功能适配，解决传统调试工具部署形态单一、场景适配局限、界面老旧、协议适配单一、设备兼容受限的痛点，全面覆盖桌面开发调试、在线快速调试、开发内嵌调试多类场景，降低设备开发调试的学习与操作成本。

项目全程基于 **Vibe Coding 模式** 开发，**所有技术栈选型严格遵循「AI大模型高熟悉度、社区主流、资料丰富、生态成熟」原则**，杜绝冷门、小众、迭代停滞、AI训练数据覆盖少的技术与语法，最大化保障AI编码准确率、减少纠错成本、提升整体开发效率。

## 调研发现

- 主流工具Modbus Poll交互逻辑不合理，调试不连续寄存器时，每读取一个不连续寄存器需要单独开启一个窗口，操作繁琐、调试效率极低
- 安川原厂Mamep2006使用体验优秀、功能布局贴合调试习惯，但属于内部专属软件，无公开使用权限，仅支持Windows桌面端部署，适配场景单一，无法适配开发者多环境使用需求
- 安川原厂Mamep2006存在明确功能BUG：设备COM编号超过10时软件无法正常识别、使用，多串口设备调试场景兼容性极差，严重影响开发调试效率
- 现有开源Modbus调试工具大多功能单一、部署形态固化，部分仅支持单一Modbus协议，无法同时兼容Modbus TCP与Modbus RTU调试场景，且不支持私有协议扩展，无法适配安川等品牌设备的开发调试需求
- 传统桌面调试软件普遍沿用老旧Windows经典设计，保留File、View等传统顶层菜单栏，设计冗余、操作层级繁琐，是老式Windows应用的遗留样式，不符合现代桌面软件设计规范
- 多数开发调试软件布局老旧、UI设计简陋、配色落后，视觉观感差，新用户容易因界面陈旧、操作复古繁琐产生抵触心理，缺乏现代化极简设计优化
- 现有调试工具无多端适配方案：浏览器端可通过Web Serial API支持标准Modbus RTU调试，但无法支持Modbus TCP网络调试，导致多数工具三端RTU功能不统一、在线调试场景缺失，开发者无法灵活切换使用
- 部分老旧调试工具技术栈封闭、文档稀少、生态老旧，AI适配度极低，不适合Vibe Coding快速迭代开发模式，选型不当极易出现代码生成错误、语法陈旧、无人维护等问题

## 核心痛点总结

1. 不连续多寄存器调试操作繁琐，多窗口切换严重影响开发调试效率
2. 优质专属调试工具私有化、不公开，通用工具功能简陋、适配性差
3. 常规工具协议适配不统一，多数工具无法实现三端一致的Modbus RTU调试能力，且TCP/RTU双协议难以兼顾
4. 原厂Mamep2006存在串口兼容BUG，COM编号＞10无法使用，无法适配多串口调试场景
5. 常规工具不支持私有协议扩展，无法适配品牌设备专属调试场景
6. 传统调试软件沿用老旧Windows经典菜单栏（File、View等冗余顶层菜单），设计老旧、操作繁琐，不符合现代软件交互逻辑
7. 老旧调试工具界面设计陈旧、颜值偏低，用户观感差，新用户上手意愿低，缺乏现代化UI优化
8. 工具部署形态单一、三端协议适配不一致，无法适配浏览器在线RTU调试、桌面深度调试、VSCode开发内嵌调试的多元使用场景
9. 传统调试工具开发技术栈偏老旧、小众、封闭，**不适配AI驱动的Vibe Coding开发模式**，编码纠错成本高、迭代速度慢

## 核心需求

1. 核心功能：支持单表格布局，单行读取单个寄存器，可批量调试不连续寄存器，无需多窗口切换；**三端统一Modbus RTU全量能力，差异化适配Modbus TCP协议**，适配不同客户端环境限制；修复原厂软件缺陷，支持COM10以上串口设备正常识别与调试，解决多串口设备兼容问题。
   - 浏览器端：受浏览器网络安全策略限制，**不支持Modbus TCP协议调试**；完整兼容支持Modbus RTU全量调试功能，与Electron、VSCode端RTU能力完全对齐，包含串口连接、全编号串口适配、寄存器读写、数据校验、日志查看等全套能力，满足在线RTU设备快速调试、方案配置与预览需求。
   - Electron客户端：完整实现全部双协议功能，支持Modbus TCP、Modbus RTU全量调试、全编号串口设备适配、私有插件扩展、完整数据读写校验等所有核心能力，对标并超越原厂Mamep2006全场景调试能力。
   - VSCode插件端：完整落地全部开发调试核心功能，**Modbus RTU能力与另外两端完全一致**，同时支持Modbus TCP协议调试，适配编辑器开发场景，优化内嵌交互形态，实现开发、调试一体化，功能完整、展示形态适配VSCode插件规范。
2. 界面适配：三端统一核心功能布局与操作逻辑，完全对标经典Mamep2006调试逻辑，贴合老用户使用习惯、降低学习成本；**舍弃老式Windows经典设计，彻底去除冗余的File、View等传统顶层菜单栏**，采用现代极简交互设计。对界面配色、控件样式、视觉细节、交互逻辑进行全端现代化升级，摒弃老旧复古控件样式。实现「老用户熟悉功能、新用户认可颜值」的效果，三端保持视觉风格统一，同时根据各端载体特性微调布局，适配不同终端展示规范。
3. 架构设计：采用插件化架构，实现公私功能分离，核心业务逻辑三端通用，通过环境适配层区分各端TCP协议差异化能力，RTU核心逻辑全端统一，降低多端维护成本。
4. 开源规范：公开Modbus通用协议（TCP/RTU）实现、基础界面功能、三端适配框架，开源至公共代码平台。
5. 扩展能力：私有协议、不可公开功能以独立插件形式加载，安川公开私有协议可作为开源插件范例，三端统一支持插件体系。
6. 基础能力：三端完全统一Modbus RTU调试能力，Electron、VSCode端额外支持Modbus TCP调试，全面覆盖各类开发调试场景，保障各端功能稳定、操作简洁高效。
7. 技术选型规范（Vibe Coding专属）：全程选用**AI大模型训练充分、社区活跃度高、主流通用、文档公开丰富**的成熟技术栈，优先前端通用主流技术体系，坚决规避小众封闭、停止维护、语法诡异、资料稀缺的冷门技术，保证AI可稳定、准确、高质量生成全量业务代码，适配快速迭代开发模式。
8. 对于寄存器表，暂时只支持使用03/10功能码进行读写，在此表中，不支持其他功能进行读写。其他功能码的支持会使用与这个不同的寄存器表，属于待支持功能，例如：在侧边栏选择只支持coils的表，这个表只使用coils相关寄存器（只是例子，不一定会真的追加）
9. Enter RAM/Enter ROM 等安川专用按键由插件实现；Address Adjust 已确认进入核心（Connection Settings 配置项，ON 时发送地址 = 用户地址 − 1，默认 OFF）
10. 小工具一类的支持会放在插件中实现，且没有实现RPN Calculator的计划。
11. 对于像串口设置（除串口号外）所有可设定的值都要在重新打开时恢复成关闭前的状态，打开的寄存器表标签页也要恢复，寄存器表中的内容也要恢复。
12. 为了保证质量，会采用测试驱动开发/验收测试驱动的 Vibe Coding
