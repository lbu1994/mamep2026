# 2. 产品概述

## 2.1 产品简介

Mamep2026 是一款面向设备开发人员和嵌入式开发人员的轻量化、现代化、可扩展 Modbus 开发调试工具。

产品借鉴 M@MEp2006 高效的单表格寄存器调试方式，在保留“不连续寄存器集中管理、单行独立读写、批量读取、周期轮询”等核心体验的同时，重新设计现代化用户界面，并支持以下三种部署形态：

1. 浏览器在线工具；
2. Electron 桌面客户端；
3. VSCode 插件。

Mamep2026 同时支持 Modbus RTU 和 Modbus TCP，并根据不同运行环境的能力边界进行差异化适配：

| 客户端          | Modbus RTU | Modbus TCP |
| --------------- | ---------: | ---------: |
| 浏览器端        |       支持 |     不支持 |
| Electron 客户端 |       支持 |       支持 |
| VSCode 插件端   |       支持 |       支持 |

产品主要面向开发人员自用和研发调试场景，不作为工业生产控制系统、功能安全系统或无人值守设备监控系统使用。

## 2.2 产品愿景

打造一款比传统 Modbus 工具更容易使用、比 M@MEp2006 更现代、比单一桌面工具更灵活，并且适合 AI 驯化、生成和持续迭代的跨平台调试工具。

## 2.3 核心价值

1. 使用一张表管理任意不连续寄存器，不需要为每个地址创建独立窗口；
2. 三端保持一致的核心操作逻辑，降低环境切换时的学习成本；
3. 修复 M@MEp2006 无法正常使用 COM10 以上串口的问题；
4. 同时覆盖在线快速调试、桌面深度调试和 VSCode 内嵌调试场景；
5. 通过插件机制隔离通用开源能力和设备厂商私有能力；
6. 采用现代化界面，移除老式 Windows 顶层菜单和过时控件；
7. 采用主流、成熟、AI 熟悉度高的技术体系，降低 Vibe Coding 的生成和纠错成本；
8. 通过测试驱动和验收测试驱动方式保障核心通信功能质量。

## 2.4 产品目标

### 2.4.1 必须达成的目标

1. 提供单表格、不连续寄存器集中调试能力；
2. 三端实现一致的 Modbus RTU 核心调试能力；
3. Electron 和 VSCode 端支持 Modbus TCP；
4. 正确识别和使用 COM10 及以上串口；
5. 支持保持寄存器的读取与写入；
6. 支持单行读取、单行写入、全表读取和周期轮询；
7. 支持配置、标签页和寄存器表内容的会话恢复；
8. 提供通信日志、运行消息和当前通信参数查看能力；
9. 提供插件化扩展边界，避免把私有协议写入核心产品；
10. 保持三端的数据模型、操作概念和主要界面结构一致。

### 2.4.2 非目标

1. 不定位为工业生产控制软件；
2. 不提供功能安全认证；
3. 不承诺用于无人值守的长期连续监控；
4. 不提供完整 PLC、HMI 或 SCADA 功能；
5. 不以复刻 M@MEp2006 的老式视觉风格为目标；
6. 不复刻 M@MEp2006 的授权信息、访问计数器、品牌区和用户信息区；
7. 不在核心产品中实现安川专用 Enter RAM、Enter ROM（Address Adjust 已确认进入核心，见 §6.3 连接配置与 §6.5.6）；
8. 不在核心产品中提供 RPN Calculator；
9. 不在初始版本中支持全部 Modbus 功能码；
10. 不在初始版本中提供工业级权限管理、审计和防误操作管控。

# 3. 目标用户

## 3.1 核心用户

### 3.1.1 嵌入式软件开发人员

主要任务：

- 调试设备的 Modbus RTU 或 Modbus TCP 通信；
- 验证寄存器地址、数据格式和读写行为；
- 同时观察多个不连续寄存器；
- 检查原始请求、响应和异常报文；
- 在固件开发过程中快速修改设备参数。

核心诉求：

- 操作直接；
- 不需要频繁切换窗口；
- 原始报文透明；
- 支持串口和网络两种连接；
- 能在 VSCode 中完成基本调试。

### 3.1.2 设备应用开发人员

主要任务：

- 配置设备参数；
- 验证设备协议实现；
- 根据寄存器清单进行批量调试；
- 保存不同设备或场景的寄存器表。

核心诉求：

- 表格配置易于保存和恢复；
- 支持多个标签页；
- 支持备注和多种数值显示格式；
- 能快速复制已有寄存器配置。

### 3.1.3 通信协议开发和测试人员

主要任务：

- 验证不同串口配置；
- 检查通信异常、超时、重试和校验行为；
- 比较读写前后的设备数据；
- 定位 Modbus 异常码和报文格式问题。

核心诉求：

- 完整日志；
- 清晰的错误分类；
- 可配置超时、重试和写后回读；
- 能查看实际下发和接收的原始数据。

## 3.2 次要用户

1. 现场调试工程师；
2. 测试工程师；
3. 自动化设备方案开发人员；
4. 需要临时在线调试串口设备的开发者；
5. 需要通过插件支持厂商私有扩展的设备开发团队。

## 3.3 不作为主要目标的用户

1. 没有通信协议基础的普通消费者；
2. 需要工业生产级权限和审计能力的运维人员；
3. 需要长期无人值守监控的工厂操作人员；
4. 需要完整组态和可视化大屏的 SCADA 用户；
5. 需要功能安全、防误写联锁和认证体系的安全关键系统用户。

# 4. 典型使用场景

## 4.1 浏览器快速调试

用户通过浏览器打开 Mamep2026，授权访问本地串口，配置波特率等参数后连接 Modbus RTU 设备，在寄存器表中读取、写入和周期监控设备数据。

适用场景：

- 临时调试；
- 无法安装桌面软件；
- 展示或培训；
- 快速验证串口设备。

限制：

- 不支持 Modbus TCP；
- 串口能力受浏览器和操作系统支持情况限制；
- 用户必须主动授权串口访问。

## 4.2 Electron 桌面深度调试

用户安装桌面客户端，通过串口连接 Modbus RTU 设备，或通过 IP 地址和端口连接 Modbus TCP 设备，使用完整寄存器调试、日志、会话恢复和插件能力。

适用场景：

- 日常设备开发；
- 多串口环境；
- 完整日志分析；
- 私有协议插件扩展；
- 长时间调试。

## 4.3 VSCode 内嵌调试

用户在开发固件或上位机程序时，通过 VSCode 侧边栏、编辑区或面板打开 Mamep2026，无需离开开发环境即可读取和修改设备寄存器。

适用场景：

- 固件编码和设备调试同步进行；
- 在项目工作区中保存调试表；
- 开发、测试和问题定位一体化。

## 4.4 不连续寄存器集中监控

用户在同一个表格中配置多个不连续地址，例如 0001、0100、0900 和 F100，分别定义名称和数据显示类型，然后通过单行读取、全表读取或周期轮询查看数据。

系统不要求寄存器地址连续，也不要求用户为不同地址创建多个窗口。

## 4.5 多设备或多场景配置

用户为不同设备、功能模块或调试阶段创建多个寄存器表标签页。关闭并重新打开应用后，系统恢复标签页、寄存器内容和通信参数。

# 6. 核心功能需求

## 6.1 应用工作区

### 6.1.1 总体布局

应用主界面由以下区域组成：

1. 顶部应用栏；
2. 左侧工作区侧边栏；
3. 中央多标签页区域；
4. 标签页内寄存器操作栏；
5. 核心寄存器表格；
6. 底部消息与通信日志面板；
7. 当前连接状态展示区域。

### 6.1.2 顶部应用栏

应提供以下入口：

- 新建寄存器表；
- Connection Settings（打开连接配置，使用 Modal，每次应用启动自动弹出）；
- 连接/断开切换按钮（单个按钮：离线时显示 CONNECT，在线时显示 DISCONNECT）；
- 当前连接状态（文字 + 语义色，不只用颜色表达）；
- 当前协议类型；
- Plugin Manager（插件管理）；
- Settings（全局设置）；
- 帮助或关于信息。

连接配置、插件管理和全局设置的入口统一放置在顶部应用栏；侧边栏仅用于寄存器表（标签页）列表。

不得沿用 File、Edit、View、Communication、Option、Window、Tools 等老式顶层菜单结构。

常用操作应直接出现在工具栏、上下文菜单或对应功能区域中。

---

## 6.2 连接管理

### 6.2.1 连接类型

用户创建连接时，应先选择：

1. Modbus RTU；
2. Modbus TCP。

浏览器端只显示或只允许选择 Modbus RTU。不得提供一个可以点击但必然失败的 Modbus TCP 入口。

### 6.2.2 连接状态

至少包含以下状态：

- 未连接；
- 正在连接；
- 已连接；
- 正在断开；
- 连接失败；
- 连接中断；
- 正在重连或等待重试。

界面必须明确展示当前状态，不能只依靠按钮颜色表达。

### 6.2.3 连接互斥

同一工作区在 MVP 阶段只维持一个活动连接。

所有打开的寄存器表共享当前活动连接及当前从站地址。

多连接并行能力不属于 MVP 范围，可在后续版本评估。

### 6.2.4 连接失败行为

连接失败时：

1. 保持未连接状态；
2. 保留用户已经填写的配置；
3. 展示可理解的失败原因；
4. 提供重新连接入口；
5. 不清空寄存器表；
6. 不自动反复连接，除非用户明确启用了重试或自动重连能力。

与原 M@MEp2006 不同，连接失败后不应强制关闭配置界面，使用户能够直接修改参数并重试。

## 6.3 Modbus RTU 配置

### 6.3.1 串口号

要求：

1. 自动枚举当前可用串口；
2. 支持 COM1 至 COM9；
3. 支持 COM10 及以上串口；
4. 支持非 Windows 平台的串口命名方式；
5. 串口列表支持刷新；
6. 浏览器端使用浏览器授权机制选择设备；
7. 串口不存在或已占用时给出明确提示；
8. 串口号不要求在重启后自动恢复连接；
9. 不应因为保存的串口已不存在而阻塞应用启动。

> **浏览器侧实现说明（2026-08-15，浏览器 MVP 验收后）**
>
> - 第 1、5 条在浏览器端由 Web Serial 授权 picker 承担：`BrowserPlatformHost.requestSerialPort()` 调 `navigator.serial.requestPort()` 打开系统原生设备选择器，每次打开即实时枚举当前可用设备（等同「自动枚举 + 刷新」）；因此浏览器端不提供自定义串口列表与刷新按钮，能力矩阵声明为 `serialPorts: "browser-picker"`；
> - 第 2~4 条由浏览器/操作系统层处理，无 COM 编号上限（本质规避了原工具 COM10 bug）；
> - 第 7 条由 `WebSerialTransport.mapSerialError()` 映射：`NotFoundError→SERIAL_DEVICE_DISCONNECTED`、`InvalidStateError→SERIAL_PORT_IN_USE`、`SecurityError→SERIAL_PERMISSION_DENIED`；
> - 第 8、9 条：`recentPortHint` 仅提示不自动连接，串口不存在不阻塞启动；
> - `navigator.serial.getPorts()` 只能返回已授权端口、无法枚举未授权设备（Web Serial 隐私模型），当前已声明但未调用。

### 6.3.2 波特率

至少支持：

- 1200；
- 2400；
- 4800；
- 9600；
- 19200；
- 38400；
- 57600；
- 115200。

MVP 使用固定选项，避免非法输入。后续版本可评估自定义波特率。

默认值：9600。

### 6.3.3 数据位

支持：

- 7 位；
- 8 位。

默认值：8 位。

### 6.3.4 停止位

支持：

- 1 位；
- 2 位。

默认值：1 位。

如果某个客户端运行环境支持 1.5 位停止位，可在能力检测后提供；不得为了界面一致性，在底层不支持时显示不可用选项。

### 6.3.5 校验位

支持：

- None；
- Even；
- Odd。

默认值：None。

### 6.3.6 流控

目标选项：

- OFF；
- XON/XOFF；
- RTS/CTS。

各端仅展示或启用实际支持的模式。不支持的模式应隐藏或明确标记不可用，不得静默降级。

默认值：OFF。

### 6.3.7 从站地址

要求：

1. 使用数字选择或数字输入控件；
2. 默认值为 1；
3. 允许范围为 0 至 255（2026-08 已确认）；
4. 从站地址 0 属于广播地址语义；MVP 不实现广播写入，配置为 0 时设备按标准不会应答，请求按超时或失败处理；
5. 对不适用于当前操作的地址给出明确提示；
6. 所有寄存器表默认共享当前从站地址；
7. 从站地址修改后，对后续请求立即生效；
8. 已经在队列中执行的请求不应被中途修改。

MVP 不提供每行独立从站地址。

### 6.3.8 接收延迟（Rx Delay）

要求：

1. 支持设置相邻请求之间的最小附加间隔（内部字段 interRequestDelayMs）；
2. 同时作为 WP 行周期轮询的重复读取间隔（不设独立的全局轮询间隔配置）；
3. 默认值为 50 ms（2026-08 已确认）；
4. 至少覆盖 0 至 100 ms；
5. 用户能够明确看到单位；
6. 具体作用时点由技术设计文档定义。

### 6.3.9 超时

要求：

1. 用户可配置单次请求响应超时时间；
2. 必须显示时间单位；
3. 应提供合理默认值；
4. 超时后进入重试或失败处理；
5. 超时不能导致整个应用无响应。

### 6.3.10 重试次数

要求：

1. 支持 0 至 10 次；
2. 默认值为 1；
3. 重试结束后仍失败，应返回最终失败状态；
4. 每次重试应在日志中可识别。

### 6.3.11 RTU 校验方式

MVP 核心产品仅提供标准 Modbus RTU 所需的 CRC-16。

BCC、CHECK-SUM 等非标准或私有校验方式不进入核心产品，应通过插件扩展。

适用端：

配置项：

1. 主机名或 IP 地址；
2. TCP 端口；

## 6.5 寄存器表

### 6.5.1 表格定位

MVP 首先提供“保持寄存器表”。

该表只支持：

- 读取保持寄存器：功能码 03；
- 写入多个保持寄存器：功能码 0x10，即十进制 16。

即使单次只写一个 16 位寄存器，仍使用功能码 0x10。

其他功能码不应混入该表格。未来支持线圈、离散输入或输入寄存器时，应使用独立的表类型。

### 6.5.2 表格列

固定顺序如下：

1. 行号（No）；
2. TM（轨迹追踪，复选框，勾选后弹出 Memory Trace 追踪窗口）；
3. 名称（Name）；
4. 寄存器地址（Register[HEX]）；
5. WP（周期轮询开关，每行独立）；
6. 读取（READ 按钮，按钮内必须包含完整的 “READ” 文字，可同时配图标但不得只有图标）；
7. 数据（Data）；
8. 写入（WRITE 按钮，按钮内必须包含完整的 “WRITE” 文字，可同时配图标但不得只有图标）；
9. 数据类型（Type）；
10. 备注（Comment）。

不设独立的状态或错误提示列（Status 列）。地址与输入错误在对应单元格内提示，读写结果与错误通过底部消息面板和通信日志展示。

> 实现注记（2026-08-15，见 [ADR-015](adr/ADR-015-行编辑交互与剪贴板决策.md)）：浏览器 MVP 在表格最前增加多行选择复选框列（Ant Design Table `rowSelection` 原生能力：表头全选、Shift 范围选择、Ctrl 多选），实际列序为「[选择列] No / TM / Name / Register[HEX] / WP / READ / Data / WRITE / Type / Comment」。

MVP 不要求复刻原工具中的 TM 和 WP 控件样式，应使用现代且含义明确的开关、按钮和提示；WP 列使用现代开关控件，不复刻原工具的笑脸锁定交互。

### 6.5.3 行号

要求：

- 自动生成；
- 从 1 开始；
- 仅表示表格顺序；
- 不等于寄存器地址；
- 行增删和移动后自动更新。

### 6.5.4 TM 列（轨迹追踪）

**控件类型：** 复选框

**作用说明：**

- 轨迹追踪使能标记；勾选该复选框后，会独立弹出专属数据追踪小窗口，对当前行配置的寄存器数值进行持续增量刷新更新，自动保留完整历史变化数据，实现寄存器数据动态轨迹监视效果。
- 未勾选时无弹窗追踪效果，仅支持常规手动单次读取操作。

**TM 追踪弹窗完整界面与功能详情：**

- 弹窗标题固定为 `M@MEp2006 Advance [Memory Trace]`
- 顶部自动回显当前监控参数信息，包含：
  - **Name** 输入框：同步所选行 Name 列内容
  - **Address** 输入框：同步所选行 Register 列 4 位十六进制地址
  - **Type** 下拉框：同步所选行 Type 数据格式
- 内置 **Play**、**Stop**、**Save** 三大功能按钮，分别用于启动追踪、暂停追踪、导出保存追踪数据
- 右侧配备 **Buffer Size** 下拉缓冲区配置，可选档位：`Continue`、`100`、`500`、`1000`、`1500`、`2000`、`3000`，用于限制或持续采集历史数据条数；`Continue` 并非真正无限，内部使用环形缓冲区硬上限（10000 条）防止内存无限增长
- 同时配有 **Speed** 速度调节刻度，上为 Quick（快速）、下为 Slow（慢速），可自定义数据刷新频次
- 窗口主体为数据列表表格，表头为 No.、Data：
  - **No.** 代表读取次序编号
  - **Data** 为对应采样数值
  - 增量滚动刷新并留存完整时序记录
- 弹窗底部设有 **Average** 平均值显示输入框，点击 Stop 停止追踪后，自动计算并展示本次已采集所有数据的平均值

### 6.5.5 名称

要求：

- 用户可自由填写；
- 允许为空；
- 用于说明寄存器含义；
- 支持复制和粘贴；
- 随标签页内容一起保存和恢复。

名称历史建议不进入 MVP，避免历史数据无限增长和跨项目污染，可在后续版本评估。

### 6.5.6 寄存器地址

要求：

1. 按十六进制输入和显示；
2. 默认显示为 4 位大写十六进制；
3. 不足 4 位时自动补零；
4. 接受用户输入小写字符，并自动转换为大写；
5. 自动去除首尾空格；
6. 非法字符应在当前单元格中明确提示；
7. 地址为空时不发送请求；
8. 超出有效范围时不发送请求；
9. 地址校验失败时，不应无提示地清空用户输入；
10. 全表读取时跳过无效地址，并汇总提示；
11. 每行地址相互独立，允许任意不连续地址。

Address Adjust 由核心产品提供，位于 Connection Settings 中（ON 时发送地址 = 用户地址 − 1，默认 OFF，2026-08 已确认）。通信日志必须同时记录用户输入地址与实际发送地址。

### 6.5.7 WP 列（周期轮询）

要求：

1. 每行通过 WP 开关独立开启或关闭周期轮询；
2. 轮询开启后，按 Connection Settings 中的 Rx Delay（interRequestDelayMs，默认 50 ms）作为重复读取间隔；
3. 不提供独立的全局轮询间隔配置，也不提供全部行持续轮询（ALL Polling）功能；全表读取为一次性批量操作；
4. 每个寄存器使用独立的功能码 03 请求；
5. 不自动合并连续地址；
6. 同一连接上的请求应有序执行，避免串口请求并发冲突；
7. 用户断开连接时立即停止或取消后续轮询；
8. 行被删除或地址变更时，旧轮询任务必须停止；
9. 周期轮询期间，数据单元格默认作为只读结果展示；
10. 编辑或准备写入时不暂停该行轮询：Data 单元格采用单一当前值模型（读取结果与待写值共用同一输入区域，无独立写入输入态、草稿或提交事务），读取成功结果无条件强制覆盖单元格内容，包括用户正在输入时（已确认决策，详见 §20.4）；
11. 应明确展示当前行是否正在轮询。

### 6.5.8 单行读取

读取按钮显示完整文字 “READ”（可配图标）。点击读取按钮后：

1. 校验连接状态；
2. 校验当前行地址是否有效；
3. 校验寄存器地址；
4. 使用功能码 03 读取一个 16 位保持寄存器；
5. 成功后更新 Data；
6. 失败后保留错误状态；
7. 记录请求和响应日志；
8. 不影响其他行是否开启周期轮询。

### 6.5.9 全表读取（Read All，一次性）

全表读取是一次性批量操作，不提供全表持续轮询。全表读取应：

1. 遍历当前标签页的所有行；
2. 只处理地址合法的行；
3. 跳过空行和地址非法行；
4. 每行独立发送功能码 03 请求；
5. 不自动合并连续地址；
6. 按可预测顺序执行；
7. 支持用户取消尚未执行的任务；
8. 展示总行数、成功数、失败数和跳过数；
9. 单行失败不应中断整个批次；
10. 将每次请求记录到通信日志。

### 6.5.10 数据列

Data 列采用 Ant Design 表格可编辑单元格交互，输入框宽度铺满单元格（width: 100%），点击单元格任意空白区域均可进入编辑状态。职责如下：

1. 展示读取结果，格式随该行 Type；
2. 作为普通输入框，允许用户直接输入要写入的值；
3. 点击 Write 时对输入执行 Type 格式与 16 位范围校验；
4. 读取成功返回新内容时，无条件强制覆盖单元格已有内容，包括用户正在输入时；
5. 读取失败时，单元格内容保持不变，不做提示；
6. 通信日志照常记录每次读取失败。

### 6.5.11 单行写入

写入按钮显示完整文字 “WRITE”（可配图标）。点击写入按钮后：

1. 校验连接状态；
2. 校验当前行地址是否有效；
3. 校验寄存器地址；
4. 校验输入值；
5. 将输入值转换为 16 位原始值；
6. 使用功能码 0x10 写入一个保持寄存器；
7. 根据 Read Verify 配置决定是否回读；
8. 展示写入或回读结果；
9. 记录完整通信日志。

写入失败时：

- 不清空单元格内容；
- 显示失败原因；
- 允许用户修改后重试。

### 6.5.12 写后回读

支持以下产品行为：

- OFF：写入成功后不回读；
- ON：写入成功后立即回读；
- ON 100 ms：等待 100 ms 后回读；
- ON 200 ms：等待 200 ms 后回读；
- ON 500 ms：等待 500 ms 后回读。

回读使用功能码 03。

结果必须区分：

1. 写入失败；
2. 写入成功且回读成功，值一致；
3. 写入成功且回读成功，值不一致；
4. 写入成功但回读失败。

回读失败不能被错误地展示为写入失败。

### 6.5.13 数据类型

MVP 支持以下 16 位显示类型：

- HEX；
- Unsigned Dec.；
- Unsigned 0.1；
- Unsigned 0.01；
- Unsigned 0.001；
- Unsigned 0.0001；
- Signed Dec.；
- Signed 0.1；
- Signed 0.01；
- Signed 0.001；
- Signed 0.0001；
- Binary。

通用规则：

1. Type 只改变 Data 的解释、输入和显示方式；
2. 不改变底层寄存器原始 16 位数据；
3. 切换 Type 后应基于同一原始值重新显示；
4. 有符号类型使用 16 位有符号数解释；
5. 无符号类型使用 16 位无符号数解释；
6. Binary 显示为固定 16 位；
7. HEX 显示为固定 4 位大写十六进制；
8. 缩放类型应明确小数位；
9. 写入时必须验证转换后的原始值是否处于 16 位范围；
10. 无法精确表示的输入，应提示用户，不得静默产生不可预测结果。

Endian Type 对单个 16 位寄存器通常不产生可感知差异。MVP 不将其作为核心表格配置项。未来支持 32 位或多寄存器数据类型时再统一规划字节序和字序。

### 6.5.14 行编辑

支持：

- 新增行；
- 插入行；
- 删除行；
- 向上移动；
- 向下移动；
- 复制；
- 剪切；
- 粘贴；
- 多行选择；
- 键盘快捷操作；
- 右键上下文菜单。

删除包含数据的行时应支持撤销，或提供适当的防误操作机制。

> **已确认行为（2026-08-15，见 [ADR-015](adr/ADR-015-行编辑交互与剪贴板决策.md)）**
>
> - 浏览器 MVP 已完整实现上述全部条目（含本属 §8.3 P1 的 多行选择 / 剪切 / 粘贴，经用户确认提前到本轮）。
> - **插入行**：在当前选中行**下方**插入一个**空行**，不继承名称 / 地址 / 类型等字段；行号自动重排。
> - **删除**：采用直接删除，**不弹确认弹窗、不引入撤销/重做**（用户明确：删除弹窗影响调试体验，不视为缺口；本条覆盖上文「应支持撤销或提供适当防误操作机制」）。多选删除同样不弹窗。
> - **剪贴板**：同时实现系统剪贴板与应用内剪贴板。系统剪贴板为 CSV 文本（表头 `Name,Register,Data,Type,Comment`，Register 列用十进制数值）；应用内剪贴板跨标签页生效；系统剪贴板不可用时回退应用内剪贴板。
> - **键盘快捷键**：Alt+↑/↓ 上移/下移、Delete 删除、Ctrl+C / Ctrl+X / Ctrl+V 复制/剪切/粘贴、Ctrl+I 插入；焦点位于文本输入控件（单元格编辑等）时不拦截。
> - **右键上下文菜单**：插入上方 / 插入下方 / 上移 / 下移 / 复制 / 剪切 / 粘贴 / 删除。
> - **多行选择**：采用 Ant Design Table `rowSelection` 原生能力（选择复选框列、表头全选、Shift 范围选择、Ctrl 多选）；选中状态为会话态，不随工作区持久化。

### 6.5.15 表格容量

产品应支持用户持续新增行。

MVP 的推荐目标：

- 普通表格包含 1000 行时仍能正常编辑；
- 开启轮询的行数应受到通信带宽和轮询周期约束；
- 系统不承诺所有行都能在极短周期内完成刷新；
- 当配置的轮询量超过通信链路能力时，应提示实际刷新频率可能下降。

## 6.6 多标签页管理

### 6.6.1 标签页功能

支持：

- 新建；

- 复制；

### 6.6.2 默认标签页

默认表可以编辑。是否允许删除由产品体验决定，但删除最后一个标签页后，系统应自动创建一个新的空白表，避免工作区无内容。

## 6.7 状态恢复和持久化

## 6.7.1 必须恢复的数据

应用重新打开后，应恢复：

1. 上次打开的标签页；
2. 标签页顺序；
3. 标签页名称；
4. 每个标签页的寄存器行；
5. 名称；
6. 地址；
7. TM（轨迹追踪）；
8. 数据类型；
9. Comment（备注）内容；
10. 轮询配置状态（WP 开关）；
11. 面板展开或折叠状态；
12. 通信参数（含 Rx Delay、Address Adjust 等 Connection Settings 配置）；
13. 超时和重试配置；
14. 写后回读配置；
15. 主题和界面偏好。

## 6.7.2 串口号恢复规则

除串口号外，其他串口设置在重新打开时应恢复为关闭前状态。

串口号不作为必须恢复项，原因包括：

- 浏览器端需要重新授权；
- 串口设备路径可能变化；
- 保存的设备可能已不存在；
- 自动选择旧串口可能导致误连接。

即使客户端保存了最近使用的串口，也只能作为提示，不得自动建立连接。

## 6.7.3 连接恢复规则

应用启动时默认保持离线。

不得在未获得用户明确配置的情况下自动连接设备。

后续版本可以提供用户主动启用的“启动后自动连接”选项，但必须清楚提示风险。

## 6.7.4 数据保存时机

用户进行以下操作后应自动保存：

- 修改标签页；
- 修改寄存器行；
- 调整设置；
- 调整布局；
- 关闭标签页；
- 关闭应用。

异常退出后，应尽可能恢复最近一次已成功保存的状态。

## 6.8 消息和日志面板

### 6.8.1 面板结构

底部面板至少包括：

1. 消息；
2. 通信日志；
3. 通信属性；
4. 备注。

面板支持展开、折叠和调整高度。

### 6.8.2 消息

用于显示：

- 应用启动；
- 连接成功；
- 连接失败；
- 连接断开；
- 配置错误；
- 批量任务完成；
- 自动保存失败的错误提示（自动保存成功不提示）；
- 插件加载结果；
- 非通信类错误。

每条消息应包含：

- 时间；
- 级别；
- 简短说明；
- 可选的详细信息。

### 6.8.3 通信日志

通信日志界面只展示每条记录的请求与响应原始字节，不解析、不展示功能码等协议字段：

- 时间；
- 方向（Request / Response）；
- Request bytes / Response bytes（十六进制，大写，字节间空格分隔）。

内部数据模型仍保留协议类型、从站地址、功能码、寄存器地址、耗时、状态、异常码、重试序号等结构化字段，用于后续扩展与诊断，但不在通信日志界面中展示。

支持：

- 自动滚动；
- 暂停滚动；
- 清空；
- 复制。

通信日志中的二进制报文应使用易读的十六进制形式展示。

### 6.8.4 通信属性

展示当前活动连接的只读摘要。

RTU 示例信息：

- 串口；
- 波特率；
- 数据位；
- 停止位；
- 校验位；
- 流控；
- 从站地址；
- 超时；
- 重试；
- 连接状态。

TCP 示例信息：

- 主机；
- 端口；
- Unit ID；
- 超时；
- 重试；
- 连接状态。

### 6.8.5 备注

提供自由文本区域，用于记录：

- 设备型号；
- 固件版本；
- 测试记录；
- 寄存器说明；
- 临时调试信息。

备注应随工作区自动保存。

## 6.9 侧边栏

侧边栏仅用于展示寄存器表（标签页）列表，点击切换当前标签页，不复刻 M@MEp2006 的 Amode、Rmode 和老式树结构。

Connection Settings（连接配置）、Plugin Manager（插件管理）和 Settings（全局设置）的入口统一放置在顶部应用栏，不放侧边栏。

MVP 不提供 Memory Access 模式。

MVP 不提供以下 M@MEp2006 扩展功能：

- Register Dump；
- Register Sequence；
- Register Trace；
- Register BOOK；
- Comm. Test；
- E2P Explore；
- Memory Dump；
- Memory Sequence；
- Memory BOOK。

这些能力可根据优先级在后续版本或插件中实现。

## 6.10 插件体系的产品需求

### 6.10.1 产品目标

插件体系用于：

# 9. 关键用户流程

## 9.1 打开应用与 RTU 连接

1. 用户打开应用（每次启动都会自动弹出 Connection Settings 连接配置 Modal）；
2. 系统自动打开 Connection Settings Modal（浏览器端仅提供 Modbus RTU 配置）；
3. 选择或授权串口；
4. 配置波特率、数据位、停止位、校验位、从站地址（0~255）、Rx Delay、Address Adjust 等参数；
5. 点击 CONNECT（连接/断开为同一个切换按钮）；
6. 系统显示连接状态；
7. 用户输入寄存器地址；
8. 点击 READ（单行读取）；
9. 系统发送功能码 03；
10. Data 显示结果；
11. 日志展示请求和响应原始字节。

## 9.2 写入寄存器

1. 用户选择目标行；
2. 输入合法地址；
3. 选择数据类型；
4. 在 Data 单元格中直接输入要写入的值；
5. 点击写入；
6. 系统执行格式和范围校验；
7. 使用功能码 0x10 写入；
8. 若启用 Read Verify，则执行回读；
9. 展示写入和回读结果；
10. 通信日志记录完整过程。

## 9.3 周期监控

1. 用户配置多个不连续地址；
2. 为目标行开启 WP 轮询；
3. 在 Connection Settings 中设置 Rx Delay（作为轮询间隔）；
4. 系统按 Rx Delay 间隔依次读取各行；
5. Data 持续更新；
6. 用户关闭某行 WP 轮询；
7. 系统停止该行后续任务；
8. 其他行继续运行。

## 9.4 重新打开应用

1. 用户关闭应用；
2. 系统保存工作区；
3. 用户再次打开；
4. 系统保持离线；
5. 恢复标签页、寄存器表和界面状态；
6. 恢复除串口号外的通信配置；
7. 用户重新选择串口并连接。

# 10. 界面设计要求

## 10.1 设计原则

1. 现代、简洁、专业；
2. 保留 M@MEp2006 高效的操作逻辑，不复刻其视觉样式；
3. 高频操作直接可见；
4. 低频操作放入设置、上下文菜单或插件区域；
5. 避免多层菜单；
6. 使用明确文字配合图标，不依赖难以理解的图标；
7. 状态和错误必须可见；
8. 三端视觉一致，但遵循各平台交互规范；
9. 高信息密度与可读性并重；
10. 优先支持键盘和鼠标高效操作；
11. 连接建立、进入调试阶段后，尽量减少打断式弹窗与让用户选择的操作，保证调试流程流畅；调试中的修改操作优先内联完成（反面教材：Modbus Poll 修改参数经常需要右键选择、弹窗修改）。

## 10.2 视觉风格

建议方向：

- 现代开发工具风格；
- 中性灰作为基础背景；
- 单一品牌强调色；
- 在线、警告和错误使用语义色；
- 浅色和深色主题；
- 扁平化控件；
- 适度圆角；
- 清晰的边界和层级；
- 不使用老式立体凸起按钮；
- 不复制浅绿、白色交替行的原始样式。

表格可使用轻微的斑马纹或悬停高亮，但必须保证深色主题下的对比度。

## 10.3 主界面建议结构

### 顶部

- 产品名称；
- 当前连接摘要；
- 连接和断开按钮；
- 新建表；
- 设置；
- 插件；
- 帮助。

### 左侧

- 寄存器表列表；
- 新建表入口；
- 连接入口；
- 插件入口。

### 中央

- 多标签页；
- 当前标签页工具栏；
- 寄存器表格。

### 底部

- 消息；
- 通信日志；
- 通信属性；
- 备注。

## 10.4 寄存器工具栏

建议包含：

- 全表读取（Read All，一次性批量读取）；
- 新增行；
- 删除选中行；
- 当前从站地址；
- 当前任务状态。

不提供开始/停止全部轮询按钮（不支持 ALL Polling），也不提供全局轮询间隔配置（WP 轮询间隔 = Connection Settings 中的 Rx Delay）。

Enter ROM 和 Enter RAM 不出现在核心工具栏中。插件启用后，可以通过插件贡献的按钮出现。

## 10.5 连接配置形式

连接配置使用 Modal，每次应用启动自动弹出（2026-08 已确认）。

连接配置应：

- 按 RTU 和 TCP 分组；
- 只展示当前协议相关配置；
- 支持在失败后直接修改；
- 显示字段说明和有效范围；
- 将主要连接按钮置于明显位置；
- 提供刷新串口列表（浏览器端由授权 picker 承担：每次打开 picker 即实时刷新设备列表，无独立刷新按钮）；
- 清楚显示浏览器授权状态。

不需要显示：

- 品牌 Logo；
- 授权用户；
- Access Counter；
- 版权装饰；
- 与连接无关的信息。

## 10.6 响应式要求

窗口宽度不足时：

1. 侧边栏可折叠；
2. 底部面板可折叠；
3. 表格允许横向滚动；
4. 关键列优先显示；
5. 操作按钮可以收纳，但不得隐藏连接状态；
6. 不应强行压缩导致地址和数据不可读。

# 11. 技术栈建议

本节只给出产品级技术选型建议和约束，不定义具体工程配置、依赖版本、模块组织和实现代码。

## 11.1 选型原则

所有技术选型应满足：

1. AI 模型训练覆盖充分；
2. 社区活跃；
3. 文档公开且完整；
4. 长期维护风险较低；
5. 跨平台生态成熟；
6. TypeScript 支持良好；
7. 自动化测试生态成熟；
8. 浏览器、Electron 和 VSCode 可复用；
9. 避免小众 DSL 和封闭框架；
10. 避免为追求技术新颖而增加复杂度。

## 11.2 推荐技术体系

### 核心语言

- TypeScript。

理由：

- 三端均可使用；
- AI 熟悉度高；
- 静态类型有利于通信和数据转换逻辑；
- 前端、Electron 和 VSCode 生态统一；
- 便于共享核心业务模型。

### 前端框架

- React。

理由：

- 社区成熟；
- 资料丰富；
- AI 生成准确率较高；
- 适用于浏览器、Electron 和 VSCode Webview；
- 表格、状态管理和测试工具丰富。

### 构建工具

- Vite。

### 桌面客户端

- Electron。

理由：

- 与 Web 技术栈一致；
- 串口和 TCP 能力成熟；
- AI 和社区资料丰富；
- 可最大化复用 React 界面和 TypeScript 核心逻辑。

### VSCode 插件

- VSCode Extension API；
- Webview 用于复杂寄存器表界面；
- TypeScript 作为插件端语言。

### 状态管理

优先选择主流、轻量、可测试的 React 状态管理方案。

具体选型由技术设计文档决定，但应避免：

- 过度复杂的全局状态体系；
- 大量隐式副作用；
- 状态和通信逻辑直接耦合；
- 三端分别维护三套独立状态模型。

### 表格组件

优先选择：

- 主流；
- 支持虚拟滚动；
- 支持单元格编辑；
- 支持键盘操作；
- 支持多行选择；
- 可在 Electron、浏览器和 VSCode Webview 复用；
- 许可证符合开源要求的表格方案。

是否使用第三方表格库，应在技术设计阶段通过原型验证。

### 串口能力

- 浏览器端使用 Web Serial 能力；
- Electron 和 VSCode 使用 Node.js 生态中成熟的串口方案。

### TCP 能力

- Electron 和 VSCode 使用 Node.js TCP 能力；
- 浏览器端不实现直接 Modbus TCP。

### 测试

推荐形成以下测试层级：

- 纯函数单元测试；
- 协议行为测试；
- 状态和任务调度测试；
- 组件测试；
- 三端适配测试；
- 端到端验收测试；
- 虚拟 Modbus 设备集成测试。

具体测试框架和配置属于技术设计文档或 AGENTS.md。

## 11.3 不建议采用的技术

1. 停止维护的前端框架；
2. 小众桌面 UI 框架；
3. 仅适用于 Windows 的旧式控件框架；
4. 缺乏 TypeScript 类型定义的关键依赖；
5. 无可靠测试能力的串口库；
6. 强依赖闭源服务的核心实现；
7. 大量自定义元编程或特殊语法；
8. 为三端分别使用完全不同的前端框架；
9. 在核心通信逻辑中直接绑定具体 UI 框架；
10. AI 训练数据覆盖明显不足的冷门工具链。

# 12. 代码风格和架构模式要求

本节只定义产品对代码质量和架构的约束，不提供具体目录、接口、类、函数和编码规则。

## 12.1 总体架构要求

产品应采用以下方向：

1. 核心业务逻辑与界面分离；
2. Modbus 协议逻辑与串口、TCP 传输分离；
3. 平台能力通过适配层接入；
4. 浏览器、Electron 和 VSCode 共享核心模型；
5. 插件功能与核心功能隔离；
6. 持久化逻辑与业务状态分离；
7. 通信任务可被测试替代和模拟；
8. 错误必须结构化，不依赖字符串判断；
9. 避免全局可变状态；
10. 避免 UI 组件直接操作串口或 TCP。

推荐采用分层架构和 Ports and Adapters 思想，但具体分层方案由技术设计文档确定。

## 12.2 模块边界

产品概念上应至少区分：

- 协议核心；
- 传输能力；
- 通信会话；
- 寄存器表；
- 数据类型转换；
- 轮询和任务队列；
- 工作区和持久化；
- 日志；
- 插件；
- 平台适配；
- 用户界面。

## 12.3 代码质量要求

1. TypeScript 开启严格类型检查；
2. 核心数据不得滥用宽泛类型；
3. 通信协议数据应有明确模型；
4. 输入必须在进入核心逻辑前校验；
5. 通信错误必须可分类；
6. 公共逻辑必须可独立测试；
7. 三端不得复制粘贴核心协议代码；
8. 复杂逻辑应有测试表达预期行为；
9. 不允许通过吞掉异常维持表面运行；
10. 不允许把厂商私有规则硬编码到核心模块。

## 12.4 Vibe Coding 约束

1. 每个功能先定义验收条件；
2. 核心通信逻辑在用户要求测试时优先测试先行；
3. 一次变更聚焦一个明确目标；
4. AI 生成代码必须经过类型检查，测试执行时机由用户决定（详细规则见 AGENTS.md）；
5. 不接受仅凭界面看起来正常即判定功能完成；
6. 协议行为必须通过可重复测试验证；
7. 依赖库使用公开稳定 API；
8. 避免生成难以理解的大型单文件；
9. 避免没有测试保护的大范围重构；
10. 详细 AI 操作规则应写入 AGENTS.md，而不是写入本文档。

# 13. 限制条件

## 13.1 产品定位限制

1. 面向开发调试，不面向生产控制；
2. 不提供工业级安全联锁；
3. 不保证设备写入操作无风险；
4. 用户应自行确认寄存器地址和允许写入范围；
5. 工具不理解未知设备寄存器的业务含义；
6. 工具无法自动判断某个合法 Modbus 写入是否会导致设备故障。

## 13.2 协议限制

MVP：

- 只提供保持寄存器表；
- 只读取一个 16 位寄存器；
- 只写入一个 16 位寄存器；
- 读取使用功能码 03；
- 写入使用功能码 0x10；
- 不自动合并请求；
- 不支持线圈；
- 不支持离散输入；
- 不支持输入寄存器；
- 不支持自定义功能码；
- 不支持广播写入流程；
- 不支持多寄存器组合数据类型。

## 13.3 浏览器限制

1. 不支持 Modbus TCP；
2. 串口支持依赖浏览器和操作系统；
3. 必须由用户主动授权设备；
4. 页面刷新或关闭可能使连接中断；
5. 浏览器可能限制后台页面的任务执行频率；
6. 不承诺页面处于后台时仍保持精确轮询周期；
7. 无法访问浏览器没有授权的本地设备。

## 13.4 VSCode 限制

1. 界面运行在 VSCode 规范约束下；
2. 插件关闭、重载或 VSCode 重启会断开连接；
3. 工作区信任状态可能限制插件能力；
4. 不应阻塞 VSCode 扩展宿主；
5. 长时间任务必须允许取消；
6. UI 必须兼容 VSCode 主题。

## 13.5 Electron 限制

1. 桌面客户端体积通常高于原生轻量工具；
2. 串口权限可能受到操作系统安全策略影响；
3. macOS、Linux 和 Windows 的串口命名及权限模型不同；
4. 插件和本地能力必须考虑桌面安全边界；
5. 应避免界面层直接获得不必要的系统权限。

# 14. 边界场景

## 14.1 串口场景

必须处理：

- 系统没有串口；
- COM10 及以上；
- 串口在列表刷新后出现（浏览器端：重新打开授权 picker 即看到新插入设备）；
- 串口在连接前消失；
- 串口被其他程序占用；
- 连接后设备被拔出；
- 串口权限不足；
- 浏览器拒绝授权；
- 浏览器撤销授权；
- 配置的参数不被当前环境支持；
- 设备持续返回无效 CRC；
- 收到不完整报文；
- 响应长度异常；
- 响应从站地址不匹配；
- 响应功能码不匹配。

## 14.2 TCP 场景

必须处理：

- 主机名为空；
- IP 地址格式错误；
- 端口非法；
- DNS 解析失败；
- 连接超时；
- 对端拒绝连接；
- 连接后立即断开；
- 请求过程中断线；
- 响应事务不匹配；
- 响应 Unit ID 不匹配；
- 自动重连过程中用户主动断开。

## 14.3 表格场景

必须处理：

- 空地址；
- 地址包含非法字符；
- 地址超过 4 位；
- 地址越界；
- 重复地址；
- 大量空白行；
- 删除正在轮询的行；
- 修改正在轮询的地址；
- 复制包括无效数据的多行；
- 粘贴数据超过当前表格长度；
- 切换标签页时仍有任务运行；
- 关闭存在轮询任务的标签页；
- 全表读取过程中断开连接；
- 批量读取过程中用户取消；
- 同一地址存在于多行；
- 同一地址以不同 Type 显示。

重复地址允许存在，每行按独立配置处理。

## 14.4 数据输入场景

必须处理：

- HEX 中输入非法字符；
- Binary 中输入非 0 和 1；
- 无符号类型输入负数；
- 有符号类型超出 16 位范围；
- 小数位超过类型精度；
- 输入空值；
- 输入前后有空格；
- 粘贴本地化数字格式；
- 输入极大数值；
- 类型切换后原值无法按新类型表示。

## 14.5 并发和任务场景

必须处理：

- 用户连续快速点击读取；
- 用户连续快速点击写入；
- 轮询过程中执行手动读取；
- 轮询过程中执行写入；
- 全表读取与周期轮询同时触发；
- 切换连接时仍有请求排队；
- 请求超时后迟到响应到达；
- 重试期间用户断开；
- 插件请求与核心请求同时发送。

同一通信连接必须保证请求不会以不可控方式并发发送。

具体任务优先级和调度策略由技术设计文档定义。

## 14.6 状态恢复场景

必须处理：

- 保存内容损坏；
- 保存失败；
- 磁盘空间不足；
- 浏览器存储不可用；
- 上次版本数据结构与当前版本不一致；
- 应用异常退出；
- 标签页部分保存成功；
- 恢复时插件不存在；
- 恢复时保存的串口不存在。

发生恢复错误时，应尽可能保留可恢复数据，并允许用户重置工作区。

# 15. 非功能性需求

## 15.1 性能

### 启动性能

建议目标：

- 常规设备上首次可交互时间不超过 3 秒；
- 恢复普通工作区时不应出现长时间白屏；
- 插件加载不应阻塞核心界面显示；
- 单个插件异常不应拖延整个应用启动。

### 表格性能

建议目标：

- 1000 行寄存器配置可正常滚动和编辑；
- 普通单元格编辑响应时间不超过 100 ms；
- 日志持续增长时界面仍保持可操作；
- 大量行时采用适当渲染优化；
- 切换标签页不应重复创建无必要的通信任务。

### 通信性能

1. 软件额外处理延迟应远低于实际串口或网络通信时间；
2. 请求调度不得阻塞界面线程；
3. 轮询周期小于实际完成时间时，不应无限累积任务；
4. 应展示实际刷新能力受波特率、超时、重试和行数限制；
5. 不承诺毫秒级实时控制性能。

## 15.2 稳定性

1. 单次通信错误不得造成应用崩溃；
2. 设备拔出后应用保持可操作；
3. 插件崩溃不得破坏核心工作区；
4. 日志过大时应有上限或归档策略；
5. 状态保存失败必须提示；
6. 应支持安全释放串口和 TCP 连接；
7. 关闭标签页和应用时不得遗留不可控任务；
8. 核心协议转换逻辑应具备充分自动化测试。

## 15.3 安全性

虽然产品不承担工业安全职责，仍需满足基础软件安全要求：

1. 界面代码不得直接获得不必要的系统权限；
2. 对所有用户输入进行校验；
3. 插件安装和启用需要明确提示；
4. 不默认执行未知插件；
5. 不记录不必要的敏感信息；
6. 日志导出前提醒可能包含设备地址和通信数据；
7. 不自动把调试数据上传到云端；
8. 不在用户不知情时建立外部网络连接；
9. 桌面客户端遵循 Electron 基础安全要求；
10. VSCode 插件遵循工作区信任和扩展权限约束。

## 15.4 隐私

默认情况下：

- 所有配置保存在本地；
- 不要求用户登录；
- 不采集设备通信内容；
- 不上传寄存器表；
- 不上传原始报文；
- 不上传插件私有数据。

如果未来添加遥测，必须：

1. 默认透明；
2. 明确说明采集内容；
3. 不包含原始设备报文和寄存器数据；
4. 提供关闭方式；
5. 遵守开源项目隐私说明。

## 15.5 可用性

1. 首次使用者应能在不阅读完整帮助文档的情况下完成连接、填写地址和读取寄存器；
2. 高频操作应在主界面直接可见；
3. 所有输入项应显示名称、单位、有效范围或示例；
4. 禁用的操作应说明禁用原因；
5. 错误提示应描述问题及可执行的解决方法，避免只显示内部错误代码；
6. 连接、读取、写入和轮询应提供明确的进行中状态；
7. 长时间操作应允许取消；
8. 用户执行失败的操作后，已输入内容不得被无提示清空；
9. 相同操作在浏览器、Electron 和 VSCode 三端应保持相近的名称、位置和行为；
10. 专业术语应保持一致，不应在不同界面混用不同名称。

## 15.6 可访问性

建议满足以下要求：

1. 所有核心功能均可通过键盘完成；
2. 提供清晰可见的键盘焦点；
3. 表格支持方向键、Tab 和 Shift+Tab 导航；
4. 图标按钮应提供文字说明或辅助标签；
5. 不仅依靠颜色表达在线、离线、成功、警告和失败状态；
6. 浅色和深色主题下均保持足够的文字对比度；
7. 用户缩放界面后，核心操作仍可使用；
8. 错误信息应与对应输入控件建立明确关联；
9. 动态更新的数据不应导致焦点意外跳转；
10. 周期轮询不应通过持续闪烁表达状态；
11. 尽可能兼容屏幕阅读器对常用控件和表格的识别；
12. 不要求 MVP 达成正式无障碍认证，但不得采用明显阻碍键盘用户的交互设计。

## 15.7 兼容性

### 操作系统

Electron 客户端和 VSCode 插件应优先支持：

- Windows 10；
- Windows 11；
- 当前仍受主流社区支持的 macOS 版本；
- 主流桌面 Linux 发行版。

Windows 是串口调试和 COM10 以上场景的重点验证平台。

### 浏览器

浏览器端应优先支持具备 Web Serial 能力的 Chromium 系浏览器。

如果当前浏览器不支持所需能力，产品应：

1. 在进入连接流程前完成能力检测；
2. 明确提示不支持的能力；
3. 提供可行的替代方案说明；
4. 不显示虚假的连接成功状态；
5. 仍允许用户查看界面或已有工作区数据，但不得执行不可用的串口操作。

### VSCode

VSCode 插件应声明最低兼容版本，并在不兼容时提供明确提示。

具体最低版本和支持周期在发布计划中确定，不在本 PRD 中固定。

## 15.8 可维护性

1. 三端共享的产品行为应保持一致；
2. 同一缺陷不应要求在三套独立业务实现中分别修复；
3. 平台不支持某项能力时，应通过能力差异明确表达，不应复制一套行为相近但规则不同的功能；
4. 核心 Modbus 功能与厂商私有功能必须保持边界；
5. 新增插件不应要求修改核心寄存器表的既有业务规则；
6. 工作区数据升级应考虑向后兼容；
7. 用户数据无法迁移时，应提供备份、导出或重置路径；
8. 产品发布前应对关键通信流程执行回归验收；
9. 已知限制应在发布说明中公开；
10. 详细模块依赖、数据迁移机制和接口稳定性策略由技术设计文档定义。

## 15.9 可测试性

产品功能应具备明确、可重复的验收方式。

重点覆盖：

1. RTU 连接成功和失败；
2. TCP 连接成功和失败；
3. COM10 及以上串口；
4. 功能码 03 单行读取；
5. 功能码 0x10 单行写入；
6. 写后回读；
7. 不连续地址全表读取；
8. 周期轮询启动和停止；
9. 超时和重试；
10. 无效地址和无效数据；
11. 设备断开；
12. 标签页和寄存器表恢复；
13. 三端一致性；
14. 插件加载失败隔离；
15. 大量表格行和日志记录。

测试数据和测试设备应覆盖正常响应、超时、异常响应、无效校验和连接中断。

具体测试框架、测试目录、模拟器实现和执行命令不属于本 PRD，应在技术设计文档和 AGENTS.md 中定义。

## 15.10 国际化

MVP 至少应确保：

1. 界面文本集中管理，避免文案散落在业务逻辑中；
2. 支持中文和英文界面扩展；
3. 通信术语翻译保持一致；
4. 数值输入和协议转换不受界面语言影响；
5. 十六进制地址始终按照协议规则处理；
6. 日志中的原始报文不进行本地化；
7. 时间显示可以使用用户所在环境的本地格式；
8. 导入和导出数据应使用稳定字段，不依赖当前界面语言。

MVP 可先交付一种主要界面语言，但产品结构不得阻碍后续增加其他语言。

# 16. 产品验收标准

## 16.1 核心调试闭环

满足以下条件，可认为产品具备基础可用性：

1. 用户可以创建或恢复寄存器表；
2. 用户可以建立支持的 RTU 或 TCP 连接；
3. 用户可以在同一表格中配置多个不连续地址；
4. 用户可以使用功能码 03 读取单个保持寄存器；
5. 用户可以使用功能码 0x10 写入单个保持寄存器；
6. 用户可以执行全表读取；
7. 用户可以开启和停止单行周期轮询；
8. 用户可以查看格式化数值和原始通信日志；
9. 关闭并重新打开应用后可以恢复工作区内容；
10. 连接、读取或写入失败不会导致应用崩溃或用户配置丢失。

## 16.2 Modbus RTU 验收

1. 三端均可完成 RTU 连接、读取、写入和日志查看；
2. Windows 下可以正常识别并使用 COM10 及以上串口；
3. 当前环境没有串口时，界面给出明确提示；
4. 串口被占用时，连接失败原因可理解；
5. 设备拔出后，连接状态及时更新；
6. 超时和重试行为符合用户配置；
7. 错误 CRC、响应地址不匹配和功能码不匹配能够被识别；
8. 浏览器拒绝授权后，应用保持可操作；
9. 不受支持的串口参数不会被静默接受；
10. 断开连接后不再发送新的请求。

## 16.3 Modbus TCP 验收

1. Electron 和 VSCode 可以使用主机、端口和 Unit ID 建立连接；
2. 浏览器端不显示可用的 Modbus TCP 调试入口；
3. 主机或端口非法时不发送连接请求；
4. 连接超时和对端拒绝连接时显示不同的错误信息；
5. 连接中断后停止或取消待执行请求；
6. 用户主动断开后不应被自动重连逻辑再次连接；
7. 请求和响应可在通信日志中正确关联；
8. 事务不匹配和异常响应能够被识别。

## 16.4 寄存器表验收

1. 支持任意不连续地址；
2. 地址输入不足 4 位时自动补零；
3. 地址显示为大写十六进制；
4. 非法地址不会发送请求；
5. 非法输入不会被无提示清空；
6. 重复地址允许存在；
7. 每行的数据类型可独立设置；
8. Type 切换不改变原始 16 位数据；
9. 全表读取跳过空行和地址非法行；
10. 单行失败不终止全表读取；
11. 删除正在轮询的行后，不再产生该行请求；
12. 读取失败时 Data 单元格内容保持不变，不做提示；
13. 写入失败时保留单元格内容；
14. 行编辑和多标签页操作不会破坏其他行的数据；
15. 普通 1000 行表格可以正常编辑和滚动。

## 16.5 状态恢复验收

重新打开应用后，应正确恢复：

- 标签页数量；
- 标签页名称和顺序；
- 寄存器行；
- 名称和地址；
- 数据类型；
- TM 追踪状态；
- 轮询配置；
- 通信参数；
- 超时和重试；
- 写后回读配置；
- 备注；
- 面板状态；
- 主题和用户偏好。

同时满足：

1. 应用启动时默认离线；
2. 不自动连接上次使用的设备；
3. 串口号不作为必须恢复项；
4. 保存数据损坏时不导致应用无法启动；
5. 用户可以重置损坏的工作区；
6. 恢复失败时提供明确提示。

## 16.6 三端一致性验收

以下项目在三端应使用相同的产品规则：

- 地址格式；
- 数据类型；
- 读取和写入规则；
- 全表读取跳过规则；
- 周期轮询行为；
- 超时和重试含义；
- 错误分类；
- 日志核心字段；
- 工作区核心数据；
- 插件平台能力提示。

允许存在的差异：

- 窗口布局；
- 快捷键；
- 系统权限申请方式；
- 串口选择方式；
- 主题来源；
- TCP 能力；
- 插件可使用的平台权限。

# 17. 产品成功指标

Mamep2026 面向开发者工具场景，初期不以商业转化作为首要指标，优先关注可用性、稳定性和调试效率。

## 17.1 核心指标

4. 三端 RTU 核心验收场景全部通过；

8. 高频操作不依赖深层菜单；
9. 主要用户任务可以通过键盘和鼠标完成；
10. 核心功能具备自动化回归测试。

## 17.2 建议量化目标

正式发布前建议达到：

- P0 验收用例通过率：100%；
- P1 验收用例通过率：不低于 95%；

- 单次通信失败不会导致未保存的寄存器配置丢失。

具体性能基准应结合测试环境记录，不应脱离硬件、操作系统和通信参数声明绝对结果。

# 18. 风险与应对方向

## 18.1 浏览器串口兼容性风险

风险：

- 并非所有浏览器和操作系统都支持 Web Serial；
- 权限机制可能导致三端串口选择体验不同；
- 后台页面可能被限速。

产品应对：

- 启动时检测能力；
- 明确展示支持状态；
- 提供 Electron 客户端作为完整替代；
- 不承诺浏览器后台精确轮询；
- 避免将浏览器端描述为全平台通用串口方案。

## 18.2 三端功能一致性风险

风险：

- 三端系统能力不同；
- 分别实现可能导致功能和错误处理逐步分叉。

产品应对：

- 统一核心产品规则；
- 差异只存在于平台适配能力；
- 建立跨端共同验收场景；
- 对不支持的能力明确隐藏或禁用；
- 不通过模拟成功掩盖平台限制。

## 18.3 通信任务冲突风险

风险：

- 周期轮询、单行读写、全表读取和插件请求可能同时发生；
- 串口无法安全处理无约束并发请求。

产品应对：

- 同一连接上的请求必须受控；
- 长任务支持取消；
- 断开时停止后续请求；
- 向用户展示繁忙状态；
- 具体调度策略在技术设计文档中确定。

## 18.4 插件安全和稳定性风险

风险：

- 第三方插件可能执行错误操作、访问设备数据或影响稳定性；
- 不同平台可用能力不同。

产品应对：

- 展示来源和权限；
- 支持禁用插件；
- 隔离插件加载错误；
- 声明平台兼容性；
- 核心产品不默认安装来源不明的插件；
- 插件不能绕过用户可见的能力提示。

## 18.5 设备误写风险

风险：

- 合法的 Modbus 写入仍可能对设备造成不可逆影响；
- 核心工具无法了解所有厂商寄存器语义。

产品应对：

- 明确产品用于开发调试；
- 对写入操作提供明显状态；
- 不自动执行未由用户触发的写入；
- 不在核心产品中硬编码危险厂商命令；
- 厂商专用操作由插件提供说明和必要提示；
- 不承诺替代设备厂商的安全操作规范。

## 18.6 Vibe Coding 质量风险

风险：

- AI 可能生成表面可运行但协议边界错误的代码；
- 多次快速变更可能破坏跨端一致性；
- AI 可能选用过时或不存在的 API。

产品应对：

- 核心行为由验收条件约束；
- 通信和转换逻辑在用户要求测试时采用测试先行；
- 所有变更通过类型检查；自动化测试执行时机由用户决定；
- 使用社区主流、文档充分的技术；
- 关键协议行为必须通过模拟设备或真实设备验证；
- AI 代理的具体执行规则在 AGENTS.md 中定义。

## 18.7 工作区数据兼容风险

风险：

- 后续新增字段或表类型可能导致旧数据无法读取；
- 应用异常退出可能产生不完整数据。

产品应对：

- 保存数据应包含版本信息；
- 升级时尽量兼容旧数据；
- 恢复失败时保留原始数据；
- 提供重置和导出入口；
- 具体数据格式和迁移机制在技术设计文档中定义。

# 19. 产品假设

当前规划基于以下假设：

1. 主要用户具备基础 Modbus 概念；
2. 主要使用场景是开发和测试，而非生产运行；
3. 单个活动连接可以覆盖 MVP 的主要需求；
4. 16 位保持寄存器能够覆盖第一阶段主要调试场景；
5. 每行独立报文比自动合并请求更符合目标用户的调试需求；
6. Electron 是能力最完整的客户端；
7. 浏览器端接受不支持 Modbus TCP 的限制；
8. VSCode 用户愿意在编辑器内使用 Webview 形式的寄存器表；
9. 用户需要恢复工作区，但不希望应用启动后自动连接设备；
10. 厂商私有能力适合通过插件隔离；
11. 产品初期不需要登录、云同步和团队权限管理；
12. 用户接受核心项目保持轻量，复杂工具以后续版本或插件提供。

如果上述假设在用户测试中被否定，应重新评估对应功能和版本优先级。

# 20. 待确认事项

以下内容仍需在产品评审或原型验证阶段确认。

## 20.1 从站地址范围（已确认，2026-08）

已确认（ADR-013）：RTU 从站地址允许范围 0~255，默认 1；地址 0 允许配置（广播语义，按标准无应答）；MVP 不实现广播写入。

仍待确认：

1. RTU 和 TCP 是否使用相同输入范围（TCP Unit ID 范围）；
2. 如果允许地址 0，除读写外哪些操作可用；
3. Unit ID 的界面名称是否根据协议动态变化。

## 20.2 停止位和流控支持

需要通过三端能力验证确认：

- 浏览器端是否完整支持 1.5 位停止位；
- 三端对 XON/XOFF 的支持程度；
- 三端对 RTS/CTS 的支持程度；
- 不支持参数应隐藏还是禁用显示。

## 20.3 轮询间隔（已确认，2026-08）

已确认（ADR-013）：

1. 不设独立的全局轮询间隔配置；
2. WP 轮询间隔使用 Connection Settings 中的 Rx Delay（interRequestDelayMs）；
3. 默认值为 50 ms；
4. 语义为相邻请求之间的最小附加间隔，同时作为轮询节奏来源；
5. 不提供每行独立间隔。

仍待确认：

1. 当实际通信时间超过设定间隔时的用户提示方式。

## 20.4 Data 列的读写交互

已确定采用 Ant Design 表格默认交互：

1. 读取结果和待写值共用同一个单元格输入区域，内容即当前值，无独立编辑态、草稿或提交事务；
2. 编辑不暂停该行轮询，读取成功结果强制覆盖单元格内容，包括用户正在输入时；
3. 读取失败时单元格内容保持不变，不做提示（通信日志照常记录失败）；
4. 写入时按当前 Type 解析单元格文本并校验 16 位范围，校验失败时提示且不清空单元格内容；
5. 写后回读成功时，回读结果按读取规则覆盖单元格；未启用回读时，写入完成后单元格保持用户输入值；
6. Type 切换不改写单元格文本；
7. Data 单元格编辑不纳入撤销/重做。

## 20.5 多标签页与连接关系

MVP 已假设所有标签页共享一个活动连接和从站地址。

仍需确认：

- 标签页是否需要保存期望的连接配置；
- 切换标签页是否提示配置差异；
- 后续是否允许标签页绑定不同设备；
- 插件是否可以请求独立连接。

## 20.6 插件 MVP 边界

需要确认首个可发布版本中，插件体系是：

1. 只提供内部扩展验证；
2. 支持本地安装插件；
3. 提供一个安川示例插件；
4. 提供插件开发文档；
5. 仅预留架构但不对用户开放。

如果插件安装和运行能力未达到安全和稳定要求，可以在 MVP 中保留扩展边界，在 V1.0 正式开放。

## 20.7 工作区导入导出

需要确认：

- MVP 是否需要导出配置文件；
- 是否支持 CSV；
- 是否支持完整工作区文件；
- 是否允许跨三端导入；
- 是否保存连接信息；
- 是否排除设备敏感信息；
- 文件格式是否作为公开兼容格式长期维护。

## 20.8 Memory Trace 和 Register Trace

TM 的 Memory Trace 追踪窗口已确认（ADR-013）：数据列表形式（No./Data）、Buffer Size 固定档位（Continue 硬上限 10000）、Speed 滑块控制采样间隔（100~2000ms）、支持暂停/恢复（Play/Stop）与 Save 导出，由核心产品实现（PRD §6.5.4）。

Register Trace（后续扩展）产品形式仍待确认：

- 实时曲线；
- 导出格式；
- 是否由核心产品或插件实现。

## 20.9 多标签页右键菜单

M@MEp2006 的多标签页右键菜单内容暂不明确。

Mamep2026 不需要等待原软件细节确认，可按照现代标签页通用交互设计：

- 重命名；
- 复制；
- 关闭；
- 关闭其他；
- 关闭右侧；
- 调整顺序。

最终菜单应通过原型测试确认。

# 22. 发布与版本策略

## 22.1 发布阶段

### 阶段一：内部原型

目标：

- 验证寄存器表交互；
- 验证不连续地址调试流程；
- 验证三端共享界面的可行性；
- 验证串口和 TCP 基础能力；
- 验证 COM10 以上串口；
- 验证 Data 列读写交互。

### 阶段二：MVP

目标：

- 完成 P0 功能；
- 跑通三端 RTU；
- 跑通 Electron 和 VSCode TCP；
- 完成状态恢复；
- 完成核心自动化验收；
- 提供可供开发人员实际使用的版本。

### 阶段三：V1.0

目标：

- 完成主要 P1 功能；
- 增强日志和错误处理；
- 支持工作区导入导出；
- 完善文档；
- 开放基础插件能力；
- 提供安川公开协议示例插件；
- 达到稳定公开发布条件。

### 阶段四：V1.x

目标：

- 根据用户反馈增加 Trace、Sequence、Dump 和更多数据类型；
- 扩展表类型；
- 改善多设备和多连接能力；
- 完善插件生态。

## 22.2 发布阻断条件

存在以下情况之一时，不应发布 MVP 或正式版本：

1. COM10 以上串口仍无法正常使用；
2. 核心读取或写入存在已知数据转换错误；
3. 断开连接后仍持续发送请求；
4. 写入目标地址与用户输入地址不一致；
5. Type 转换可能产生无提示的数据截断；
6. 工作区恢复会稳定导致用户配置丢失；
7. 单个通信错误会导致应用崩溃；
8. 浏览器端错误宣称支持直接 Modbus TCP；
9. 插件加载失败会阻止应用启动；
10. 三端对相同寄存器数据产生不一致解释；
11. P0 验收用例未全部通过；
12. 存在未解决的阻断级或严重级缺陷。

# 26. PRD 完成定义

当以下条件满足时，本 PRD 可以进入产品评审并作为技术设计输入：
